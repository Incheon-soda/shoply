# 00. 프로젝트 개요 & 역할

> **이 문서 하나로 프로젝트 전체를 이해한다. 헷갈리면 여기부터.**

---

## 1. 한 줄 요약

> 동일한 쇼핑몰 앱을 **온프레미스 k8s**와 **AWS EKS**에 똑같이 올리고,
> 트래픽 폭증·장애 때 **어떻게 다르게 버티는지**를 데이터로 비교하는 실험.

---

## 2. 무엇을 비교하나 (실험의 핵심)

앱·부하·설정을 **전부 똑같이** 맞추고, 딱 하나만 다르게 둔다:

| | 온프레미스 | EKS |
|---|---|---|
| 파드 자동확장 (HPA) | ✅ 동일 | ✅ 동일 |
| **노드 자동확장** ★핵심 | ❌ 없음 (고정) | ✅ Karpenter |
| DB 자동복구 *(선택)* | ❌ 수동 | ✅ RDS Multi-AZ |

→ **핵심 독립변수는 "노드 자동확장"** (시나리오 2·3). "고정 자원 vs 탄력 자원"의 운영 특성 차이를 측정한다.
> **DB 자동복구는 선택** — 시나리오 4(DB 페일오버)로 할지 **아직 미정**. 필수는 노드 확장이다.

온프레미스에서 Pending이 쌓이는 것은 **패배가 아니라 측정 대상**이다.

---

## 3. 시스템 구성 (최신 확정)

```
[온프레미스]  AWS EC2 위에 KVM 가상머신으로 k8s 클러스터 재현
  c8i.2xlarge EC2
    └── KVM 가상머신 3대
          ├── master  (k8s 컨트롤플레인)
          ├── worker1 (gateway, product, inventory)
          └── worker2 (frontend, order, payment, user)

[앱]  MSA 7개 서비스 (gateway + 6)
[이미지]  GHCR (ghcr.io/incheon-soda/shoply-*)
[DB]  온프레: EC2 PostgreSQL 16 / EKS: RDS
[부하]  k6
[모니터링]  Prometheus + Grafana (별도 EC2)
```

| 항목 | 값 |
|---|---|
| 가상화 | **KVM** (가상머신) |
| k8s 버전 | v1.34.x |
| 이미지 레지스트리 | **GHCR** (`ghcr.io/incheon-soda/shoply-*`) |
| 트래픽 진입 | Nginx Ingress (NodePort :30080) |
| 부하 도구 | k6 |

## 5. 실험 시나리오 (요약 — 상세는 05)

| | 상황 | 온프레 | EKS |
|---|---|---|---|
| **1** | 안정 (200 RPS) | 정상 (Error 0) | 정상 (동일) |
| **2 ★** | 스파이크 (급증+유지) | Pending 지속 → Error↑ | 노드추가 후 회복 |
| **3** | 워커노드 죽임 | 복구 수 분 | 복구 60초 |
| (4) | DB 죽임 (선택) | 수동 승격 | RDS 자동 |

## 6. 현재 진행 상황

**✅ 완료**
- 앱 코드 정리 (부하코드 제거, 커넥션풀, 페일오버 설정, liveness/graceful)
- 매니페스트 (리소스 100m/500m, HPA 60%, soft affinity)
- 온프레미스 KVM k8s 클러스터 구축
- HPA 작동 확인 (부하 주면 파드 증가)
- Grafana 대시보드
- DB 준비 SQL (load-test-prep)

**⬜ 남음**
- 온프레미스 최종 한계 데이터 수집 (Pending 발생 RPS)
- EKS 구축 (예정)
- DB Primary-Replica (시나리오 4, 선택)
- k6 A/B/C 스크립트 분리
- 본 실험 A → B → C

> **EKS는 아직 미구축.** 각 문서에 "EKS 예정" 섹션으로만 표기, 상세는 추후.
