## 1. 확정 아키텍처 구조

```
AWS 단일 계정 (ap-northeast-2)
│
├── VPC-A (10.0.0.0/16) ─── 온프레미스 + 공통 인프라
│   └── Public 서브넷 10.0.1.0/24 (ap-northeast-2a)
│       │
│       ├── c8i.2xlarge  [EIP]  ← 온프레미스 k8s 호스트
│       │   └── KVM
│       │       ├── VM1 Master  192.168.122.2 (2vCPU/4GB)
│       │       ├── VM2 Worker1 192.168.122.3 (2vCPU/4GB) ← traffic-node
│       │       └── VM3 Worker2 192.168.122.4 (2vCPU/4GB) ← order-node
│       │
│       ├── t3.medium           ← PostgreSQL 16
│       ├── t3.micro            ← Redis 7
│       │
│       ├── t3.small   [EIP]   ← Monitoring (Prometheus + Grafana)
│       │
│       ├── t3.medium  [EIP]   ← Locust-A → 온프레미스 LB 전용
│       └── t3.medium  [EIP]   ← Locust-B → EKS ALB 전용
│
└── VPC-B (10.1.0.0/16) ─── EKS
    ├── Public 서브넷 10.1.1.0/24 (ap-northeast-2a)
    ├── Public 서브넷 10.1.2.0/24 (ap-northeast-2b)  ← EKS 최소 2 AZ
    │
    ├── EKS Worker Node t3.medium (AZ-a) [EIP] ← traffic-node
    │   └── API Gateway, Product, Inventory 파드
    ├── EKS Worker Node t3.medium (AZ-b) [EIP] ← order-node
    │   └── Frontend, Order, Payment, User 파드
    │
    ├── RDS db.t3.medium  ← PostgreSQL 관리형
    └── t3.micro          ← Redis 7
```

**EIP가 필요한 이유:**

| EC2 | EIP 이유 |
|---|---|
| c8i.2xlarge | Locust-A가 고정 IP로 타겟, 재시작 시 IP 변경 방지 |
| Monitoring (t3.small) | EKS 워커노드 SG에 이 IP를 화이트리스트 등록 → 재시작 시 SG 재설정 방지 |
| Locust-A | ALB SG 화이트리스트 불필요 (온프레미스 타겟이므로) — 선택사항 |
| Locust-B | ALB SG에 이 IP만 허용하기 위해 필수 |
| EKS Worker Node | Monitoring이 NodePort scrape 시 고정 IP 필요 |

## 2. Security Group 규칙

### SG 간 관계 한눈에

```
[인터넷]
    │ :80                              │ :80
    ▼                                  ▼
[Locust-A SG]                     [Locust-B SG]
    │ :80 (내부)                        │ :80 (공인IP)
    ▼                                  ▼
[c8i.2xlarge SG]               [ALB SG] ── (VPC-B)
    │                               │ :30000-32767
    ├─:5432→ [PostgreSQL SG]    [Worker Node SG]
    ├─:6379→ [Redis-onprem SG]      │
    │                               ├─:5432→ [RDS SG]
    │                               └─:6379→ [Redis-EKS SG]
    │
[Monitoring SG] ─────── scrape ──→ [c8i.2xlarge SG] (NodePort)
                                → [Worker Node SG]   (NodePort)
                                → [PostgreSQL SG]    (:9187)
                                → [Redis-onprem SG]  (:9121)
                                → [Redis-EKS SG]     (:9121)
```

---

### VPC-A Security Groups

#### c8i.2xlarge SG

| 방향 | 포트 | 소스 | 이유 |
|---|---|---|---|
| 인바운드 | 80 | Locust-A SG | 부하 트래픽 수신 |
| 인바운드 | 22 | Admin IP/32 | SSH |
| 인바운드 | 6443 | Admin IP/32 | kubectl API Server |
| 인바운드 | 30000-32767 | Monitoring SG | Prometheus NodePort scrape |
| 아웃바운드 | 5432 | PostgreSQL SG | 파드 → DB |
| 아웃바운드 | 6379 | Redis-onprem SG | 파드 → Redis |
| 아웃바운드 | 443 | 0.0.0.0/0 | ECR 이미지 풀 |

> 80을 0.0.0.0/0이 아닌 Locust-A SG만 허용하는 이유:  
> 실험 중 외부에서 직접 접근을 막아 트래픽 오염 방지.  
> 관리자 확인 필요 시 Admin IP를 임시 추가.

#### PostgreSQL SG (t3.medium)

| 방향 | 포트 | 소스 | 이유 |
|---|---|---|---|
| 인바운드 | 5432 | c8i.2xlarge SG | k8s 파드 → DB |
| 인바운드 | 9187 | Monitoring SG | PostgreSQL Exporter scrape |
| 인바운드 | 9100 | Monitoring SG | Node Exporter scrape |
| 인바운드 | 22 | Admin IP/32 | SSH |
| 아웃바운드 | 전체 | 0.0.0.0/0 | — |

#### Redis-onprem SG (t3.micro)

| 방향 | 포트 | 소스 | 이유 |
|---|---|---|---|
| 인바운드 | 6379 | c8i.2xlarge SG | Product Service 파드 → Redis |
| 인바운드 | 9121 | Monitoring SG | Redis Exporter scrape |
| 인바운드 | 9100 | Monitoring SG | Node Exporter scrape |
| 인바운드 | 22 | Admin IP/32 | SSH |
| 아웃바운드 | 전체 | 0.0.0.0/0 | — |

#### Monitoring SG (t3.small) — EIP 필수

| 방향 | 포트 | 소스/목적지 | 이유 |
|---|---|---|---|
| 인바운드 | 9090 | Admin IP/32 | Prometheus UI |
| 인바운드 | 3001 | Admin IP/32 | Grafana 대시보드 |
| 인바운드 | 22 | Admin IP/32 | SSH |
| 아웃바운드 | 30000-32767 | c8i.2xlarge SG | 온프레미스 NodePort scrape |
| 아웃바운드 | 30000-32767 | 0.0.0.0/0 | EKS Worker Node NodePort scrape (cross-VPC) |
| 아웃바운드 | 9187 | PostgreSQL SG | PostgreSQL Exporter |
| 아웃바운드 | 9121 | Redis-onprem SG | Redis Exporter |
| 아웃바운드 | 9100 | PostgreSQL SG | Node Exporter |
| 아웃바운드 | 9100 | Redis-onprem SG | Node Exporter |
| 아웃바운드 | 9121 | 0.0.0.0/0 | EKS Redis Exporter (cross-VPC) |
| 아웃바운드 | 9100 | 0.0.0.0/0 | EKS Redis Node Exporter (cross-VPC) |

> cross-VPC 아웃바운드는 VPC-B SG를 참조할 수 없으므로 0.0.0.0/0 사용.  
> 인바운드 제어는 VPC-B 쪽 SG에서 Monitoring EIP를 화이트리스트로 처리.

#### Locust-A SG (t3.medium) — 온프레미스 전용

| 방향 | 포트 | 소스/목적지 | 이유 |
|---|---|---|---|
| 인바운드 | 8089 | Admin IP/32 | Locust 웹 UI |
| 인바운드 | 22 | Admin IP/32 | SSH |
| 아웃바운드 | 80 | c8i.2xlarge SG | 온프레미스 LB로 부하 트래픽 |

#### Locust-B SG (t3.medium) — EKS 전용, EIP 필수

| 방향 | 포트 | 소스/목적지 | 이유 |
|---|---|---|---|
| 인바운드 | 8089 | Admin IP/32 | Locust 웹 UI |
| 인바운드 | 22 | Admin IP/32 | SSH |
| 아웃바운드 | 80 | 0.0.0.0/0 | EKS ALB로 부하 트래픽 (cross-VPC) |

> Locust-B EIP를 VPC-B ALB SG 인바운드에 등록 → Locust-B 외 트래픽 차단.

---

### VPC-B Security Groups

#### ALB SG

| 방향 | 포트 | 소스 | 이유 |
|---|---|---|---|
| 인바운드 | 80 | Locust-B EIP/32 | 부하 트래픽만 허용 (그 외 차단) |
| 아웃바운드 | 30000-32767 | Worker Node SG | ALB → Nginx Ingress NodePort |

> 80을 Locust-B EIP만 허용하는 이유:  
> 실험 외 트래픽이 들어오면 온프레미스와 비교 기준이 달라짐.  
> 관리자 확인 필요 시 Admin IP를 임시 추가.

#### Worker Node SG

| 방향 | 포트 | 소스 | 이유 |
|---|---|---|---|
| 인바운드 | 30000-32767 | ALB SG | ALB → Nginx Ingress NodePort |
| 인바운드 | 30000-32767 | Monitoring EIP/32 | Prometheus NodePort scrape |
| 인바운드 | 전체 | Worker Node SG | 노드 간 통신 (CNI, pod-to-pod) |
| 인바운드 | 10250 | Worker Node SG | kubelet API |
| 인바운드 | 22 | Admin IP/32 | SSH |
| 아웃바운드 | 전체 | 0.0.0.0/0 | ECR 풀, AWS API |

> Monitoring EIP를 명시적으로 허용하는 이유:  
> 단일 IP만 NodePort에 접근 가능 → 실험 외 메트릭 오염 방지.

#### RDS SG

| 방향 | 포트 | 소스 | 이유 |
|---|---|---|---|
| 인바운드 | 5432 | Worker Node SG | k8s 파드 → RDS |

> postgresql_exporter는 EKS 내부 k8s Pod로 배포 → RDS에 내부 접근 가능.  
> Prometheus는 postgresql_exporter의 NodePort를 scrape.

#### Redis-EKS SG (t3.micro)

| 방향 | 포트 | 소스 | 이유 |
|---|---|---|---|
| 인바운드 | 6379 | Worker Node SG | k8s 파드 → Redis |
| 인바운드 | 9121 | Monitoring EIP/32 | Redis Exporter scrape |
| 인바운드 | 9100 | Monitoring EIP/32 | Node Exporter scrape |
| 인바운드 | 22 | Admin IP/32 | SSH |
| 아웃바운드 | 전체 | 0.0.0.0/0 | — |

### 2계정 전환 시 SG 변경 사항

| 변경 항목 | 내용 |
|---|---|
| Worker Node SG 인바운드 | Monitoring EIP → 그대로 유지 (EIP는 계정 이동 후에도 동일) |
| ALB SG 인바운드 | Locust-B EIP → 그대로 유지 |
| c8i.2xlarge SG 인바운드 | Locust-A SG 참조 → Locust-A EIP로 변경 (SG cross-account 참조 불가) |
| 온프레미스 SG 아웃바운드 | PostgreSQL/Redis SG 참조 → 사설IP CIDR로 변경 |

## 3. 파드 고정 배치

### 배치 전략

```
워커노드 1 (experiment-role: traffic-node)
┌────────────────────────────────────────────┐
│  API Gateway   :4000  (모든 트래픽 진입)   │
│  Product Svc   :4001  (Read 70%, 최고 RPS) │
│  Inventory Svc :4002  (SELECT FOR UPDATE)  │
│                                            │
│  [시나리오 2] 이 노드가 먼저 한계에 도달   │
└────────────────────────────────────────────┘

워커노드 2 (experiment-role: order-node)
┌────────────────────────────────────────────┐
│  Frontend      :3000  (정적, 부하 최소)    │
│  Order Svc     :4003  (Write, 20% RPS)     │
│  Payment Svc   :4004  (Write, 10% RPS)     │
│  User Svc      :4005  (로그인 1회, 최저)   │
│                                            │
│  [시나리오 3] 이 노드를 강제 종료          │
└────────────────────────────────────────────┘

HPA 추가 파드 → affinity 없음 → 스케줄러 자유 배치
  온프레미스: 양쪽 노드 꽉 참 → Pending 누적
  EKS:       Karpenter 신규 노드 추가 → Pending 해소
```

### 노드 라벨링

```bash
kubectl label node <worker-1-name> experiment-role=traffic-node
kubectl label node <worker-2-name> experiment-role=order-node
```

### nodeAffinity — 워커노드 1 고정 (API Gateway, Product, Inventory)

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: experiment-role
          operator: In
          values:
          - traffic-node
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels:
            app: <서비스명>       # 각 서비스 자신의 레이블
        topologyKey: kubernetes.io/hostname
```

### nodeAffinity — 워커노드 2 고정 (Frontend, Order, Payment, User)

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: experiment-role
          operator: In
          values:
          - order-node
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels:
            app: <서비스명>
        topologyKey: kubernetes.io/hostname
```

> `podAntiAffinity`를 `preferred`(권고)로 설정하는 이유:  
> `required`(강제)로 하면 온프레미스에서 HPA가 같은 서비스 파드를 추가할 노드를 못 찾아 Pending이 됨.  
> 이 Pending이 "자원 부족"인지 "안티어피니티 충돌"인지 구분이 안 돼 실험 결과 오염.

### Resource Requests / Limits

HPA가 동작하려면 `resources.requests.cpu`가 반드시 있어야 한다.  
없으면 Metrics Server가 사용률 계산 기준이 없어 HPA가 스케일 안 함.

| 서비스 | CPU Request | CPU Limit | Memory Request | Memory Limit |
|---|---|---|---|---|
| API Gateway | 200m | 500m | 256Mi | 512Mi |
| Product Service | 200m | 500m | 256Mi | 512Mi |
| Inventory Service | 200m | 500m | 256Mi | 512Mi |
| Order Service | 150m | 400m | 256Mi | 512Mi |
| Payment Service | 150m | 400m | 256Mi | 512Mi |
| User Service | 100m | 300m | 128Mi | 256Mi |
| Frontend | 50m | 200m | 64Mi | 128Mi |

**워커노드 1 총 Request:** 200+200+200 = **600m / 2000m (30%)**  
**워커노드 2 총 Request:** 150+150+100+50 = **450m / 2000m (22.5%)**  

→ 정상 트래픽에서 여유 있음 → 폭증 시 실제 CPU 사용이 올라 HPA 발동

### HPA 설정

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: <서비스명>-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: <서비스명>
  minReplicas: 1
  maxReplicas: 5
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60    # CPU 60% 초과 시 스케일 아웃
```

| 서비스 | minReplicas | maxReplicas | targetCPU |
|---|:---:|:---:|:---:|
| API Gateway | 1 | 5 | 60% |
| Product Service | 1 | 5 | 60% |
| Inventory Service | 1 | 5 | 60% |
| Order Service | 1 | 5 | 60% |
| Payment Service | 1 | 5 | 60% |
| User Service | 1 | 2 | 80% |
| Frontend | 1 | 2 | 80% |

### k8s NetworkPolicy

```yaml
# 1. 기본 차단 (화이트리스트 방식)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}
  policyTypes:
  - Ingress
---
# 2. Nginx Ingress → API Gateway, Frontend
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-ingress
spec:
  podSelector:
    matchLabels:
      tier: entry          # api-gateway, frontend 공통 레이블
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: ingress-nginx
---
# 3. API Gateway → 백엔드 서비스 전체
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-gateway
spec:
  podSelector:
    matchLabels:
      tier: backend        # product/inventory/order/payment/user 공통 레이블
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: api-gateway
---
# 4. 서비스 간 직접 통신
#    Order → Inventory (재고 예약)
#    Payment → Inventory (차감/해제)
#    Payment → Order (상태 변경)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-inter-service
spec:
  podSelector:
    matchLabels:
      app: inventory-service
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: order-service
    - podSelector:
        matchLabels:
          app: payment-service
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-payment-to-order
spec:
  podSelector:
    matchLabels:
      app: order-service
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: payment-service
```

## 4. 로드밸런서

### 온프레미스 — EC2 호스트 Nginx + MetalLB + Nginx Ingress

```
Locust-A (VPC-A 내부)
    │ HTTP :80
    ▼
c8i.2xlarge (공인IP/사설IP :80)
  [EC2 SG: Locust-A SG 인바운드 허용]
    │
  EC2 호스트 Nginx (리버스 프록시)
    │ proxy_pass → 192.168.122.200
    ▼
MetalLB 가상 IP (192.168.122.200)  ← L2 ARP
    │
Nginx Ingress Controller Pod
    ├── /         → Frontend Pod (워커노드 2)
    └── /api/*    → API Gateway Pod (워커노드 1)
                       ├── /api/products/*   → Product  (워커노드 1)
                       ├── /api/inventory/*  → Inventory (워커노드 1)
                       ├── /api/orders/*     → Order     (워커노드 2)
                       ├── /api/payments/*   → Payment   (워커노드 2)
                       └── /api/auth/*       → User      (워커노드 2)
```

**EC2 호스트 Nginx 설정:**
```nginx
server {
    listen 80;
    location / {
        proxy_pass         http://192.168.122.200;
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
    }
}
```

**MetalLB IP Pool:**
```yaml
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: experiment-pool
  namespace: metallb-system
spec:
  addresses:
  - 192.168.122.200-192.168.122.210
---
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: experiment-l2
  namespace: metallb-system
```

**ECR 인증 (온프레미스 — KVM VM에는 IAM Role 없음):**
```bash
aws ecr get-login-password --region ap-northeast-2 \
  | kubectl create secret docker-registry ecr-secret \
      --docker-server=<ACCOUNT_ID>.dkr.ecr.ap-northeast-2.amazonaws.com \
      --docker-username=AWS \
      --docker-password=$(cat -)
```
```yaml
# 모든 Deployment에 추가
spec:
  template:
    spec:
      imagePullSecrets:
      - name: ecr-secret
```

### EKS — AWS ALB + Nginx Ingress

```
Locust-B (VPC-A, EIP 고정)
    │ HTTP :80
    ▼
AWS ALB (VPC-B)
  [ALB SG: Locust-B EIP/32 인바운드만 허용]
    │ Target Group → Worker Node NodePort
    ▼
  [Worker Node SG: ALB SG → :30000-32767 허용]
Nginx Ingress Controller Pod
    ├── /         → Frontend Pod (워커노드 2)
    └── /api/*    → API Gateway Pod (워커노드 1)
                       └── (온프레미스와 동일한 라우팅)
```

**Nginx Ingress yaml (온프레미스·EKS 동일):**
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shoply-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-gateway
            port:
              number: 4000
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend
            port:
              number: 3000
```

## 6. PostgreSQL / Redis 역할

### PostgreSQL

| 서비스 | 테이블 | 쿼리 패턴 | 비고 |
|---|---|---|---|
| User Service | `users` | SELECT (로그인 1회) | bcrypt 검증 |
| Product Service | `products` | SELECT | Redis 캐시 미스 시만 |
| Inventory Service | `inventory` | **SELECT FOR UPDATE · UPDATE** | 동시성 핵심 — 캐시 불가 |
| Order Service | `orders`, `order_items` | INSERT · SELECT | 주문 영구 기록 |
| Payment Service | `payments` | INSERT · UPDATE | 결제 결과 + 재고 트리거 |

**SELECT FOR UPDATE — 실험의 병목 지점:**
```sql
BEGIN;
SELECT quantity, reserved FROM inventory
WHERE product_id = $1 AND size = $2
FOR UPDATE;                     -- 행 배타 락 획득
UPDATE inventory
SET reserved = reserved + $3
WHERE product_id = $1 AND size = $2;
COMMIT;                         -- 락 해제
```
동시 요청 급증 → Lock 대기 누적 → DB 커넥션 고갈 → 응답 지연 → Error Rate 상승

**실험 차이:**

| | 온프레미스 (EC2 직접) | EKS (RDS 관리형) |
|---|---|---|
| 장애 복구 | 수동 재시작 | Multi-AZ 자동 페일오버 |
| 운영 부담 | 패치·백업 직접 | AWS 자동 |
| max_connections | postgresql.conf 수동 | RDS 파라미터 그룹 |

### Redis

**Product Service만 사용. 재고는 절대 캐시 안 함.**

```
GET /api/products       → Redis HIT → 즉시 반환 (DB 쿼리 없음)
                          Redis MISS → DB SELECT → Redis 저장(60초) → 반환

GET /api/inventory/:id  → 항상 PostgreSQL (캐시 없음)
```

| 캐시 키 | TTL | 이유 |
|---|---|---|
| `products:list` | 60초 | 목록 변경 빈도 낮음 |
| `products:{id}` | 30초 | 상세 변경 빈도 낮음 (재고 미포함) |
| inventory | 캐시 안 함 | 실시간 정합성 + 실험 병목 의도 |

양쪽 환경 모두 t3.micro EC2 직접 설치 → **통제 변수 (비교 대상 아님)**
