## 1. 확정 아키텍처 구조

```
AWS 단일 계정 (ap-northeast-2)
│
├── VPC-A (10.0.0.0/16) ─── 온프레미스 + 공통 인프라
│   └── Public 서브넷 10.0.1.0/24 (ap-northeast-2a)
│       │
│       ├── c8i.2xlarge  [EIP]  ← 온프레미스 k8s 호스트
│       │   ├── EC2 호스트 Nginx (:80 → VM NodePort 포워딩)
│       │   └── LXD (브릿지: lxdbr0)
│       │       ├── VM1 Master  <LXD_IP_1>  (Ubuntu 24.04.4, 2vCPU/4GB)
│       │       ├── VM2 Worker1 <LXD_IP_2>  (Ubuntu 24.04.4, 2vCPU/4GB) ← traffic-node
│       │       └── VM3 Worker2 <LXD_IP_3>  (Ubuntu 24.04.4, 2vCPU/4GB) ← order-node
│       │       k8s: EKS 버전과 동일하게 맞춤 (v1.32.x)
│       │       ※ IP는 lxd init 시 설정한 lxdbr0 대역 기준 — lxc list로 확인
│       │
│       ├── t3.medium           ← PostgreSQL 16
│       ├── t3.micro            ← Redis 7
│       │
│       ├── t3.small   [EIP]   ← Monitoring (Prometheus + Grafana)
│       │
│       ├── t3.medium           ← Locust-A → 온프레미스 전용 (EIP 불필요)
│       └── t3.medium  [EIP]   ← Locust-B → EKS WorkerNode 직접 전용
│
└── VPC-B (10.1.0.0/16) ─── EKS
    ├── Public 서브넷 10.1.1.0/24 (ap-northeast-2a)
    ├── Public 서브넷 10.1.2.0/24 (ap-northeast-2b)  ← EKS 최소 2 AZ
    │
    ├── EKS Worker Node t3.medium (AZ-a) [EIP] ← traffic-node  ← 실험 고정 노드
    │   └── API Gateway, Product, Inventory 파드
    ├── EKS Worker Node t3.medium (AZ-b) [EIP] ← order-node    ← 실험 고정 노드
    │   └── Frontend, Order, Payment, User 파드
    ├── EKS Worker Node t3.medium               ← Karpenter 확장용 (실험 초기 idle)
    │
    ├── k8s 버전: v1.32.12 (확인됨)
    │
    ├── RDS db.t3.medium  ← PostgreSQL 관리형
    └── t3.micro          ← Redis 7
```

> **EKS 노드 3개 운용 이유:** eksctl 초기 생성 시 3개 생성됨.  
> traffic-node, order-node 2개는 실험용으로 고정 배치.  
> 3번째 노드는 Karpenter 스케일 아웃 시 활용 또는 idle 유지.

**EIP가 필요한 이유:**

| EC2 | EIP | 이유 |
|---|:---:|---|
| c8i.2xlarge | 필수 | Locust-A 타겟 고정, 재시작 시 IP 변동 방지 |
| Monitoring (t3.small) | 필수 | EKS Worker Node SG 인바운드 화이트리스트 등록 → 재시작 시 SG 재설정 방지 |
| Locust-A | **불필요** | c8i.2xlarge SG가 Locust-A SG 참조 방식으로 허용 → IP 기반 아님 |
| Locust-B | 필수 | Worker Node SG 인바운드 화이트리스트에 고정 IP 등록 필요 |
| EKS Worker Node | 필수 | Locust-B 직접 타겟 + Monitoring NodePort scrape |

## 2. Security Group 규칙

### SG 간 관계 한눈에

```
[인터넷]
    │ :80                                   │ :NodePort
    ▼                                       ▼
[Locust-A SG]                         [Locust-B SG]
    │ :80 (내부)                             │ :NodePort (공인IP, cross-VPC)
    ▼                                       ▼
[c8i.2xlarge SG]                    [Worker Node SG] ── (VPC-B)
    │ EC2 Nginx → VM NodePort               │
    ├─:5432→ [PostgreSQL SG]               ├─:5432→ [RDS SG]
    └─:6379→ [Redis-onprem SG]             └─:6379→ [Redis-EKS SG]

[Monitoring SG] ─── scrape ──→ [c8i.2xlarge SG]  (NodePort)
                            → [Worker Node SG]    (NodePort)
                            → [PostgreSQL SG]     (:9187)
                            → [Redis-onprem SG]   (:9121)
                            → [Redis-EKS SG]      (:9121)
```

## 3. 파드 고정 배치

### 배치 전략

```
워커노드 1 (experiment-role: traffic-node)
┌────────────────────────────────────────────┐
│  API Gateway   :4000  (모든 트래픽 진입)   │
│  Product Svc   :4001  (Read 70%, 최고 RPS) │
│  Inventory Svc :4002  (SELECT FOR UPDATE)  │
│                                            │
│  [시나리오 2] 이 노드가 먼저 한계에 도달   │
└────────────────────────────────────────────┘

워커노드 2 (experiment-role: order-node)
┌────────────────────────────────────────────┐
│  Frontend      :3000  (정적, 부하 최소)    │
│  Order Svc     :4003  (Write, 20% RPS)     │
│  Payment Svc   :4004  (Write, 10% RPS)     │
│  User Svc      :4005  (로그인 1회, 최저)   │
│                                            │
│  [시나리오 3] 이 노드를 강제 종료          │
└────────────────────────────────────────────┘

HPA 추가 파드 → affinity 없음 → 스케줄러 자유 배치
  온프레미스: 양쪽 노드 꽉 참 → Pending 누적
  EKS:       Karpenter 신규 노드 추가 → Pending 해소
```

### 노드 라벨링

```bash
kubectl label node <worker-1-name> experiment-role=traffic-node
kubectl label node <worker-2-name> experiment-role=order-node
```

### nodeAffinity — 워커노드 1 고정 (API Gateway, Product, Inventory)

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: experiment-role
          operator: In
          values:
          - traffic-node
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels:
            app: <서비스명>
        topologyKey: kubernetes.io/hostname
```

### nodeAffinity — 워커노드 2 고정 (Frontend, Order, Payment, User)

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: experiment-role
          operator: In
          values:
          - order-node
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels:
            app: <서비스명>
        topologyKey: kubernetes.io/hostname
```

> `podAntiAffinity`를 `preferred`(권고)로 설정하는 이유:  
> `required`(강제)로 하면 온프레미스에서 HPA가 같은 서비스 파드를 추가할 노드를 못 찾아 Pending이 됨.  
> 이 Pending이 "자원 부족"인지 "안티어피니티 충돌"인지 구분이 안 돼 실험 결과 오염.

### Resource Requests / Limits

HPA가 동작하려면 `resources.requests.cpu`가 반드시 있어야 한다.

| 서비스 | CPU Request | CPU Limit | Memory Request | Memory Limit |
|---|---|---|---|---|
| API Gateway | 200m | 500m | 256Mi | 512Mi |
| Product Service | 200m | 500m | 256Mi | 512Mi |
| Inventory Service | 200m | 500m | 256Mi | 512Mi |
| Order Service | 150m | 400m | 256Mi | 512Mi |
| Payment Service | 150m | 400m | 256Mi | 512Mi |
| User Service | 100m | 300m | 128Mi | 256Mi |
| Frontend | 50m | 200m | 64Mi | 128Mi |

**워커노드 1 총 Request:** 200+200+200 = **600m / 2000m (30%)**  
**워커노드 2 총 Request:** 150+150+100+50 = **450m / 2000m (22.5%)**

### HPA 설정

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: <서비스명>-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: <서비스명>
  minReplicas: 1
  maxReplicas: 5
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60
```

| 서비스 | minReplicas | maxReplicas | targetCPU |
|---|:---:|:---:|:---:|
| API Gateway | 1 | 5 | 60% |
| Product Service | 1 | 5 | 60% |
| Inventory Service | 1 | 5 | 60% |
| Order Service | 1 | 5 | 60% |
| Payment Service | 1 | 5 | 60% |
| User Service | 1 | 2 | 80% |
| Frontend | 1 | 2 | 80% |

## 4. 트래픽 경로 — Nginx Ingress Controller (NodePort)

ALB, MetalLB 없음. 양쪽 모두 **Nginx Ingress Controller**가 L7 라우팅 담당.  
Nginx Ingress를 NodePort로 노출 → kube-proxy가 Nginx Ingress Pod으로 라우팅.

### 온프레미스 트래픽 흐름

```
Locust-A (VPC-A)
    │ HTTP :80
    ▼
c8i.2xlarge (공인IP:80)
  [c8i SG: Locust-A SG 인바운드 허용]
    │
  EC2 호스트 Nginx (NAT 역할)
    │ proxy_pass → <VM2_LXD_IP>:30080
    ▼
kube-proxy (VM2 Worker1, traffic-node) :30080
    ▼
Nginx Ingress Controller Pod
    ├── /api/* → API Gateway Pod (:4000)
    │               ├── /api/products/*   → Product Service
    │               ├── /api/inventory/*  → Inventory Service
    │               ├── /api/orders/*     → Order Service
    │               ├── /api/payments/*   → Payment Service
    │               └── /api/auth/*       → User Service
    └── /     → Frontend Pod (:3000)
```

**EC2 호스트 Nginx 설정:**
```nginx
server {
    listen 80;
    location / {
        proxy_pass         http://<VM2_LXD_IP>:30080;    # Nginx Ingress NodePort — lxc list로 IP 확인
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
    }
}
```

> LXD VM(192.168.122.x)은 공인IP 없음 → c8i.2xlarge가 NAT 역할.  
> kube-proxy는 모든 노드에 동일 NodePort 개방 → VM2로 진입해도 Nginx Ingress Pod으로 라우팅.

### EKS 트래픽 흐름

```
Locust-B (VPC-A, EIP 고정)
    │ HTTP :30080
    ▼
EKS Worker Node (공인IP:30080)
  [Worker Node SG: Locust-B EIP/32 인바운드 허용]
    │
  kube-proxy :30080
    ▼
Nginx Ingress Controller Pod
    ├── /api/* → API Gateway Pod (:4000)
    └── /     → Frontend Pod (:3000)
```

> 온프레미스와 EKS 모두 Nginx Ingress가 L7 라우팅 — 동일한 조건.  
> ALB 없이 NodePort로 Nginx Ingress 노출 → MetalLB도 불필요.

### Nginx Ingress Controller Service (양쪽 동일)

```yaml
apiVersion: v1
kind: Service
metadata:
  name: ingress-nginx-controller
  namespace: ingress-nginx
spec:
  type: NodePort
  ports:
  - name: http
    port: 80
    targetPort: 80
    nodePort: 30080   # 고정 — 온프레미스·EKS 동일
```

### Ingress 규칙 (양쪽 동일)

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shoply-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-gateway
            port:
              number: 4000
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend
            port:
              number: 3000
```

### 서비스 타입 정리

| 서비스 | 타입 | 이유 |
|---|:---:|---|
| Nginx Ingress Controller | NodePort :30080 | 외부 진입점 — Locust 타겟 |
| API Gateway | ClusterIP | Nginx Ingress가 내부 라우팅 |
| Frontend | ClusterIP | Nginx Ingress가 내부 라우팅 |
| Product / Inventory / Order / Payment / User | ClusterIP | API Gateway가 내부 라우팅 |
| 각 서비스 메트릭 (prom-client) | NodePort :309xx | 외부 Prometheus scrape |

### NodePort 포트 고정

| 용도 | NodePort |
|---|:---:|
| Nginx Ingress (진입점) | 30080 |
| 메트릭 scrape (API Gateway) | 30400 |
| 메트릭 scrape (기타 서비스) | 30401~ |

### ECR 인증


## 6. PostgreSQL / Redis 역할

### PostgreSQL

| 서비스 | 테이블 | 쿼리 패턴 | 비고 |
|---|---|---|---|
| User Service | `users` | SELECT (로그인 1회) | bcrypt 검증 |
| Product Service | `products` | SELECT | Redis 캐시 미스 시만 |
| Inventory Service | `inventory` | **SELECT FOR UPDATE · UPDATE** | 동시성 핵심 — 캐시 불가 |
| Order Service | `orders`, `order_items` | INSERT · SELECT | 주문 영구 기록 |
| Payment Service | `payments` | INSERT · UPDATE | 결제 결과 + 재고 트리거 |

**SELECT FOR UPDATE — 실험의 병목 지점:**
```sql
BEGIN;
SELECT quantity, reserved FROM inventory
WHERE product_id = $1 AND size = $2
FOR UPDATE;                     -- 행 배타 락 획득
UPDATE inventory
SET reserved = reserved + $3
WHERE product_id = $1 AND size = $2;
COMMIT;                         -- 락 해제
```
동시 요청 급증 → Lock 대기 누적 → DB 커넥션 고갈 → 응답 지연 → Error Rate 상승

**실험 차이:**

| | 온프레미스 (EC2 직접) | EKS (RDS 관리형) |
|---|---|---|
| 장애 복구 | 수동 재시작 | Multi-AZ 자동 페일오버 |
| 운영 부담 | 패치·백업 직접 | AWS 자동 |
| max_connections | postgresql.conf 수동 | RDS 파라미터 그룹 |

### Redis

**Product Service만 사용. 재고는 절대 캐시 안 함.**

```
GET /api/products       → Redis HIT → 즉시 반환 (DB 쿼리 없음)
                          Redis MISS → DB SELECT → Redis 저장(60초) → 반환

GET /api/inventory/:id  → 항상 PostgreSQL (캐시 없음)
```

| 캐시 키 | TTL | 이유 |
|---|---|---|
| `products:list` | 60초 | 목록 변경 빈도 낮음 |
| `products:{id}` | 30초 | 상세 변경 빈도 낮음 (재고 미포함) |
| inventory | 캐시 안 함 | 실시간 정합성 + 실험 병목 의도 |

양쪽 환경 모두 t3.micro EC2 직접 설치 → **통제 변수 (비교 대상 아님)**
