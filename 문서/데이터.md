## PostgreSQL

DB명: `shoply` | 파일: `msa_shoply/db/schema.sql` / `msa_shoply/db/seed.sql`

### 테이블 구성

| 테이블 | 소유 서비스 | 역할 | 비고 |
|---|---|---|---|
| `users` | User Service | 로그인, Mock JWT 발급 | Locust 부하 시 `user_id` 사용 |
| `products` | Product Service | 상품 정보 저장 | `is_timesale`, `sale_price`, `image_url` 포함 |
| `inventory` | Inventory Service | 사이즈별 재고 관리 | 동시성 처리 핵심 — `reserved` + `version` 낙관적 락 |
| `orders` | Order Service | 주문 생성 및 상태 관리 | 상태: `PENDING → PAID → FAILED` |
| `order_items` | Order Service | 주문 상품 상세 | 주문 시점 가격 스냅샷 저장 |
| `payments` | Payment Service | 결제 처리 및 실패 기록 | **실험에서 실패율 측정하는 핵심 테이블** |

---

### 스키마 상세

> 모든 PK는 `UUID` 타입 (`gen_random_uuid()` 자동 생성)

#### `users`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | UUID | PK DEFAULT gen_random_uuid() | |
| `email` | VARCHAR(255) | UNIQUE NOT NULL | 로그인 키 |
| `password` | VARCHAR(255) | NOT NULL | bcrypt 해시 |
| `name` | VARCHAR(255) | NOT NULL | 유저명 |
| `created_at` | TIMESTAMPTZ | NOT NULL DEFAULT NOW() | |

#### `products`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | UUID | PK DEFAULT gen_random_uuid() | |
| `name` | VARCHAR(255) | NOT NULL | 상품명 |
| `price` | INTEGER | NOT NULL | 정상 가격 |
| `description` | TEXT | | 상품 설명 |
| `image_url` | VARCHAR(500) | | 상품 이미지 URL |
| `is_timesale` | BOOLEAN | NOT NULL DEFAULT FALSE | 타임세일 여부 |
| `sale_price` | INTEGER | | 할인 가격 (타임세일 시) |
| `sale_ends_at` | TIMESTAMPTZ | | 타임세일 종료 시각 |
| `created_at` | TIMESTAMPTZ | NOT NULL DEFAULT NOW() | |

#### `inventory`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | UUID | PK DEFAULT gen_random_uuid() | |
| `product_id` | UUID | NOT NULL FK → products(id) | 상품 참조 |
| `size` | INTEGER | NOT NULL | 사이즈 (240~290) |
| `quantity` | INTEGER | NOT NULL DEFAULT 0 | 실제 재고 수량 |
| `reserved` | INTEGER | NOT NULL DEFAULT 0 | 선점 중인 수량 (주문 진행 중) |
| `version` | INTEGER | NOT NULL DEFAULT 0 | 낙관적 락 버전 |
| — | — | UNIQUE(product_id, size) | 사이즈별 중복 방지 |

> `reserved`: 주문 생성 시 증가, 결제 완료/실패 시 감소  
> `version`: UPDATE 시 버전 불일치 → 재시도 → `SELECT FOR UPDATE` 없이 동시성 제어

#### `orders`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | UUID | PK DEFAULT gen_random_uuid() | |
| `user_id` | UUID | FK → users(id) | 주문자 |
| `status` | VARCHAR(20) | NOT NULL DEFAULT 'PENDING' | PENDING \| PAID \| FAILED |
| `total_price` | INTEGER | NOT NULL | 주문 총액 |
| `created_at` | TIMESTAMPTZ | NOT NULL DEFAULT NOW() | |
| `paid_at` | TIMESTAMPTZ | | 결제 완료 시각 |
| `failed_at` | TIMESTAMPTZ | | 실패 시각 |
| `failed_reason` | TEXT | | 실패 사유 |

#### `order_items`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | UUID | PK DEFAULT gen_random_uuid() | |
| `order_id` | UUID | NOT NULL FK → orders(id) | 주문 참조 |
| `product_id` | UUID | NOT NULL | 상품 ID (스냅샷) |
| `product_name` | VARCHAR(255) | NOT NULL | 상품명 스냅샷 |
| `size` | INTEGER | NOT NULL | 사이즈 |
| `quantity` | INTEGER | NOT NULL | 수량 |
| `unit_price` | INTEGER | NOT NULL | 주문 시점 단가 스냅샷 |

#### `payments`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | UUID | PK DEFAULT gen_random_uuid() | |
| `order_id` | UUID | NOT NULL FK → orders(id) | 주문 참조 |
| `method` | VARCHAR(20) | NOT NULL DEFAULT 'card' | card \| bank |
| `status` | VARCHAR(20) | NOT NULL | PAID \| FAILED \| PENDING |
| `amount` | INTEGER | NOT NULL | 결제 금액 |
| `failed_reason` | TEXT | | PAYMENT_GATEWAY_ERROR \| INSUFFICIENT_STOCK |
| `created_at` | TIMESTAMPTZ | NOT NULL DEFAULT NOW() | |

### 인덱스 전략

실제 `schema.sql` 기준 적용 인덱스.

| 인덱스명 | 테이블 | 컬럼 | 이유 |
|---|---|---|---|
| `idx_inventory_product_id` | inventory | `product_id` | 상품별 재고 조회가 자주 발생 |
| `idx_order_items_order_id` | order_items | `order_id` | 주문별 상품 목록 조회 |
| `idx_orders_status` | orders | `status` | 상태별 주문 집계 |
| `idx_orders_user_id` | orders | `user_id` | 유저별 주문 내역 조회 |
| `idx_payments_order_id` | payments | `order_id` | 주문별 결제 내역 조회 |
| `idx_products_is_timesale` | products | `is_timesale` | 타임세일 상품 필터링 쿼리 |

> `inventory`의 `UNIQUE(product_id, size)` 제약은 내부적으로 인덱스를 생성한다.

### 시드 데이터 규모

파일: `msa_shoply/db/seed.sql` (약 44,800줄 — 부하 테스트 전용 대규모 데이터)

| 테이블 | 건수 | 비고 |
|---|:---:|---|
| `users` | ~1,000명 | admin + test1~10 + 랜덤 생성 계정 |
| `products` | 456개 | 나이키·아디다스·컨버스 등 스니커즈 상품 (is_timesale 혼합) |
| `inventory` | 2,736건 | 상품 456개 × 사이즈 6단계(240~290), quantity/reserved/version 초기화 |
| `orders` | 다수 | 부하 테스트용 사전 주문 데이터 |
| `payments` | 다수 | 부하 테스트용 사전 결제 데이터 |

> 시드 적재 순서: `TRUNCATE → users → products → inventory → orders → order_items → payments`

## Redis

### 캐싱 대상

| # | 키 | TTL | 목적 | 무효화 조건 |
|:---:|---|:---:|---|---|
| 1 | `products:list` | 60초 | `GET /api/products` 폭증 시 DB 부하 완화 | 상품 정보 변경 시 |
| 2 | `products:{id}` | 30초 | 상품 기본 정보 캐싱 (재고 제외) | 상품 정보 변경 시 |
| 3 | `stats:realtime` | 3초 | 현황 페이지 주기적 갱신, 집계 쿼리 DB 과부하 방지 | TTL 만료 시 자동 갱신 |

> **주의:** `products:{id}` 캐싱 시 재고(`quantity`, `reserved`)는 포함하지 않는다. 재고는 항상 PostgreSQL에서 직접 조회한다.

---

### 캐싱하지 않는 것

**재고 수량 → PostgreSQL 직접 조회만 허용**

| 이유 | 설명 |
|---|---|
| 정합성 | Redis ↔ DB 불일치 발생 가능 |
| 실험 설계 | 재고 정합성이 실험의 핵심 측정 지표 |
| 부하 의도 | 온프레미스에서 낙관적 락(version) 충돌이 심해져야 실험이 터짐 |
| 결과 순수성 | 캐싱하면 온프레미스 부하가 희석되어 비교 의미가 사라짐 |

### API별 캐시 흐름

```
GET /api/products
  └─ Redis 확인
       ├─ HIT  → Redis 데이터 반환
       └─ MISS → DB 조회 → Redis 저장 → 반환

GET /api/products/:id
  └─ Redis 확인 (재고 제외)
       ├─ HIT  → Redis 데이터 반환
       │         + 재고(quantity/reserved)는 DB 직접 조회하여 병합
       └─ MISS → DB 조회 → Redis 저장 (재고 제외) → 반환

GET /api/stats
  └─ Redis 확인
       ├─ HIT  → Redis 데이터 반환
       └─ MISS → DB 집계 쿼리 → Redis 저장 → 반환

POST /api/orders
  └─ Redis 미사용 → DB 직접 트랜잭션 (낙관적 락 version 체크)

POST /api/payments
  └─ Redis 미사용 → DB 직접 트랜잭션
```
