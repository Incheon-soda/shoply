## K8s EC2 (호스트 + KVM VM)

| 포트 | 위치 | 용도 | SG 인바운드 소스 |
|---|---|---|---|
| 22 | EC2 호스트 | SSH | 내 IP |
| **80 / 443** | EC2 호스트 | **부하 진입** (iptables DNAT `-d 호스트IP` → MetalLB VIP 192.168.122.24x) | 0.0.0.0/0 (또는 k6 SG) |
| 9100 | EC2 호스트 | node_exporter | 모니터링 SG |
| 80 / 443 | worker3 VM | ingress-nginx (MetalLB VIP가 L2 광고, type=LoadBalancer) | 내부 |
| 30400 | master VM | gateway 메트릭 | 모니터링 SG |
| 30401 | master VM | product 메트릭 | 모니터링 SG |
| 30402 | master VM | inventory 메트릭 | 모니터링 SG |
| 30403 | master VM | order 메트릭 | 모니터링 SG |
| 30404 | master VM | payment 메트릭 | 모니터링 SG |
| 30800 | master VM | kube-state-metrics | 모니터링 SG |
| 39101 | EC2→worker1 VM | worker1 node_exporter (iptables 포워딩) | 모니터링 SG |
| 39102 | EC2→worker2 VM | worker2 node_exporter (iptables 포워딩) | 모니터링 SG |
| **39103** | EC2→worker3 VM | worker3 node_exporter (운영, iptables 포워딩) | 모니터링 SG |
| **38080** | EC2→worker1 VM | **cAdvisor** 파드별 메트릭 (iptables 포워딩 → :8080) | 모니터링 SG |
| **38081** | EC2→worker2 VM | **cAdvisor** 파드별 메트릭 (iptables 포워딩 → :8080) | 모니터링 SG |
| 6443 | master VM | K8s API | 내부 (VM 간) |

> **왜 80/443으로 들어오나? (MetalLB 진입 — doc13 11단계)**
> - ingress-nginx를 **`Service type: LoadBalancer`** 로 두면 **MetalLB**가 사설 VIP(192.168.122.24x)를 worker3에서 L2(ARP) 광고.
> - 외부 진입: `EIP(호스트EC2) → iptables DNAT(-d 호스트IP, 80/443) → MetalLB VIP → ingress(worker3) → 파드`.
>   - ⚠️ DNAT에 **`-d 호스트IP` 필수** (안 붙이면 워커의 ghcr.io pull(443)까지 가로채 ImagePullBackOff — 11_트러블슈팅 §20).
>   - ⚠️ 호스트 사설IP는 **재구축마다 바뀜** → `hostname -I`로 매번 확인 (11_트러블슈팅 §15).
> - **EKS는 NLB**가 같은 `LoadBalancer` 추상화를 구현 → 진입 경로 대칭(공정 비교). 상세는 doc13 부록 A.
> - (구버전: NodePort 30080 + 수동 DNAT 방식은 폐기 — MetalLB LoadBalancer로 대체.)

# EKS 포트 정리

> EKS 워커는 실제 EC2(공인IP 보유) → iptables 포워딩 불필요. NodePort 직접 접근.

## EKS Worker Node

| 포트 | 용도 | SG 인바운드 소스 |
|---|---|---|
| **80 / 443** | ingress-nginx (`type: LoadBalancer` → **NLB** 자동 생성, 웹 트래픽) | NLB → 워커 |
| 30400~30404 | 앱 prom-client 메트릭 | 모니터링 EIP |
| 30800 | kube-state-metrics | 모니터링 EIP |
| 9100 | node_exporter (DaemonSet, hostPort) | 모니터링 EIP |
| 전체 | 노드 간 통신 (VPC CNI) | Worker Node SG |
| 10250 | kubelet API | Worker Node SG |
| 22 | SSH | 내 IP |

> **진입은 NLB** (`Service type: LoadBalancer` + NLB 어노테이션) → k6는 `shoply.example.com`(/etc/hosts → NLB IP)로 진입.
> 온프레(MetalLB VIP)와 **같은 LoadBalancer 추상화로 대칭** (공정 비교 — doc13 부록 A).
> Prometheus 타겟(메트릭)은 그대로 각 `<워커-공인IP>:30400` ... NodePort 직접.

## 온프레 vs EKS 메트릭 접근 차이

| | 온프레미스 | EKS |
|---|---|---|
| 워커 노드 | KVM VM (NAT 뒤) | 실제 EC2 (공인IP) |
| 메트릭 접근 | EC2 → iptables DNAT → VM | 워커 공인IP 직접 |
| node_exporter 구분 | 39101/39102 (포트 변경) | 각 워커 공인IP:9100 |
| Prometheus 타겟 | K8s EC2 사설IP | 각 워커 공인IP |
