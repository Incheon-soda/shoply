# 발표 내용 정리 — 온프레미스 vs EKS

> 면접/발표에서 나올 질문과 답변, 설명 포인트를 정리한 문서.

---

## 1. 실험 핵심 메시지

> "동일한 앱, 동일한 트래픽, 다른 인프라 — 데이터가 말하게 한다"

EKS가 더 좋다는 결론을 강요하지 않는다.  
**운영 특성 차이를 숫자로 보여주고** 판단은 보는 사람 몫.

---

## 2. 우리가 시뮬레이션한 온프레미스

**"별도 HA 솔루션 없는 일반적인 온프레미스"**

```
물리 서버 1대 (c8i.2xlarge 시뮬레이션)
  └── k8s 노드 3개 (마스터 + 워커 2개)
        └── 노드 장애 → 수동 복구
```

- 파드 재스케줄: k8s 기본 기능으로 자동
- **노드 자체 복구: 사람이 직접** (노드 수동 재시작 (virsh start))
- 노드 자동 추가: 없음

---

## 3. 실제 회사들은 어떻게 하나

| 규모 | 방식 | 복구 시간 |
|---|---|---|
| 소규모 (스타트업~중소) | **수동** — 담당자 호출 후 직접 재시작 | 사람이 올 때까지 |
| 대기업 (네이버·카카오급) | VMware HA / OpenStack 자동화 | 수 분 |
| AWS EKS | Karpenter 자동 노드 추가 | **60~90초** |

> 대기업도 자동화는 하지만 — VMware HA 같은 별도 솔루션 구축이 필요하고 복잡하다.  
> EKS는 Karpenter 설정 몇 줄로 동일한 효과를 낸다.  
> **우리는 소규모~중소 온프레미스의 현실을 시뮬레이션했다.**

---

## 4. 발표 스토리 흐름

```
1단계 — 문제 제기
  "타임세일 이벤트, 온프레미스에서 얼마나 잃고 있나?"

2단계 — 실험 소개
  "동일한 앱, 동일한 트래픽, 딱 하나만 다르게 — 노드가 자동으로 늘어나냐"
  "공정한 조건에서 비교했습니다"

3단계 — 시나리오 1 (안정)
  "평상시 200 RPS에서는 온프레미스도 충분합니다 — Error 0%"
  → 신뢰 형성 (공정성 어필)

4단계 — 시나리오 2 (스파이크) ★핵심
  "타임세일 오픈처럼 갑자기 1500 RPS로 몰립니다"
  "급증 후 유지하면 — 온프레는 Pending 쌓여 계속 무너지고"
  "EKS는 Karpenter가 60~90초 만에 노드를 추가해 흡수합니다"

5단계 — 시나리오 3 (노드 장애)
  "워커노드를 죽였습니다 — 온프레미스는 N분, EKS는 60초"
  "이 시간 동안 결제 N건 = 매출 N원 손실"

6단계 — 결론
  "이 차이가 비즈니스에 미치는 임팩트는 이렇습니다"
  "운영 인력, 새벽 호출, 매출 손실"
```

## 5. 예상 질문 & 방어 논리

### Q1. "이게 온프레미스 비교 맞아요? 그냥 AWS 안에서 컨테이너 아닌가요?"

> "물리 온프레미스 시뮬레이션입니다.  
> 핵심은 **'오토스케일링 없는 고정 자원 환경'** 과 **'탄력적 클라우드'** 의 차이입니다.  
> 컨테이너냐 VM이냐가 아니라, 노드를 자동으로 늘릴 수 있냐 없냐가 본질입니다."

### Q2. "결론이 뻔하지 않아요? 오토스케일링이 이기는 건 당연한데"

> "방향은 예상 가능하지만, **숫자가 가치입니다.**  
> '온프레미스는 정확히 X RPS에서 무너지고, MTTR이 N분 vs N초,  
> 장애 중 결제 N건(=매출 N원) 손실' — 이걸 데이터로 증명했습니다."

### Q3. "온프레미스에 Cluster Autoscaler나 HA 넣으면 되는 거 아닌가요?"

> "넣을 수 있습니다. 하지만:  
> VMware HA 같은 솔루션은 별도 구축 비용과 운영 복잡도가 높습니다.  
> EKS는 Karpenter 설정 몇 줄로 동일한 효과를 냅니다.  
> **구축 난이도와 운영 부담 자체가 비교 대상입니다.**"

### Q4. "온프레미스를 일부러 불리하게 세팅한 거 아닌가요?"

> "물리 서버는 노드를 즉시 추가할 수 없습니다 (조달 리드타임).  
> 자체 HA 구성은 별도 솔루션과 운영 인력이 필요합니다.  
> **그 현실을 반영한 것이고, 이게 온프레미스의 실제 제약입니다.**"

### Q5. "테스트 코드가 없는데요?"

> "핵심 비즈니스 로직인 **재고 동시성(SELECT FOR UPDATE)**에 집중했습니다.  
> 실험 재현성과 DB 정합성을 100% 목표로 잡았습니다."

## 6. 트래픽 흐름 설명 포인트

### 온프레미스

```
k6 → c8i EC2:30080 → iptables DNAT → KVM master VM:30080
  → kube-proxy → Nginx Ingress Pod (경로 라우팅)
  → API Gateway (어느 마이크로서비스?)
  → 각 서비스 Pod
```

- **EC2 iptables DNAT**: KVM 가상머신이 공인IP 없어서 EC2가 받아 넘기는 NAT 포워딩. 경로 판단 안 함.
  - `EC2:30080 → master VM:30080` — kube-proxy가 master에도 30080 열어줌 (ALB·Nginx 통로 없음)
- **Nginx Ingress**: `/api → Gateway`, `/ → Frontend` 경로 분배
- **API Gateway**: `/api/products → Product`, `/api/orders → Order` 등 마이크로서비스 분배 + 메트릭 수집

### EKS

```
k6 → Worker Node EIP:30080 (직접)
  → kube-proxy → Nginx Ingress Pod (동일)
  → API Gateway (동일)
```

EC2 Nginx 홉 하나 없을 뿐, Nginx Ingress부터 백엔드까지 완전 동일.

## 7. HA(High Availability) 상세 정리

### HA가 뭔가

**"서버나 서비스가 죽었을 때 자동으로 살아나는 구조"**

크게 두 가지로 나뉜다:

| 종류 | 대상 | 설명 |
|---|---|---|
| **노드 HA** | 서버(노드) 자체 | 서버 죽으면 다른 서버에서 자동 복구 |
| **DB HA** | 데이터베이스 | Primary 죽으면 Replica가 자동 승격 |

---

### 온프레미스에서 노드 HA를 넣으려면

**실제 방식: VMware HA 또는 OpenStack**

```
물리 서버 A (Primary)   물리 서버 B (Standby)
     │                        │
     └──── 서로 감시 ────────┘
                │
         A가 죽으면
                │
         B가 A 위의 VM들을 자동으로 띄움
```

**필요한 것:**
- 물리 서버 최소 2대 (우리는 EC2 1대라 불가)
- VMware vSphere 라이선스 (고가)
- 또는 OpenStack 클러스터 구축 (복잡)
- 전용 스토리지 (shared storage — NFS/SAN)
- 네트워크 이중화

**→ 우리 프로젝트에 넣을 수 없는 이유:**
KVM 가상머신이 c8i.2xlarge EC2 1대 위에 있어서 c8i 자체가 죽으면 모든 게 끝남. 진짜 노드 HA는 물리 서버가 여러 대여야 의미가 있다.

---

### 온프레미스에서 DB HA를 넣으려면

**실제 방식: Patroni (PostgreSQL 전용 HA 솔루션)**

```
[Patroni]
  ├── Primary PostgreSQL   ← 평소 여기로 읽기/쓰기
  ├── Replica PostgreSQL   ← Primary 죽으면 자동 승격
  └── etcd (합의 시스템)   ← "누가 Primary냐" 결정하는 중재자

Primary 죽음 → etcd가 판단 → Patroni가 Replica 승격 → 앱 자동 재연결
```

**필요한 것:**
- PostgreSQL EC2 최소 2대 (Primary + Replica)
- etcd 클러스터 3대 (홀수여야 과반수 투표 가능)
- Patroni 설정 및 운영 지식
- 앱에서 HAProxy 또는 VIP 엔드포인트 연결

**구축 난이도:** 높음 (설정 복잡 + EC2 비용 추가 + 운영 지속 필요)

---

### 우리 프로젝트 HA 현황

| HA 종류 | 상태 | 이유 |
|---|:---:|---|
| **노드 HA** | ❌ 불가 | 물리 서버 1대 (EC2 1대) — 구조적 한계 |
| **DB HA** | ⬜ 미구현 | Patroni 구축 복잡 (시나리오 4 DB는 선택) |
| **EC2 Nginx 이중화** | ❌ 미적용 | master VM 단일 proxy_pass (HA는 upstream 추가하면 가능) |
| **파드 재스케줄** | ✅ k8s 기본 | 노드 장애 시 살아있는 노드로 파드 이동 시도 |

---

### EKS가 HA를 어떻게 해결하나

| 문제 | 온프레미스 | EKS |
|---|---|---|
| 노드 죽음 | 수동 복구 | **Karpenter** — 새 노드 자동 생성 (60~90초) |
| DB 죽음 | 수동 승격 (Patroni 없으면) | **RDS Multi-AZ** — 자동 페일오버 (60초) |
| 파드 죽음 | k8s 재스케줄 (동일) | k8s 재스케줄 (동일) |

EKS는 Karpenter + RDS Multi-AZ 설정이 **몇 줄**로 끝난다.  
온프레미스는 VMware HA + Patroni = **수 주의 구축 작업 + 지속적 운영**.

---

### 발표에서 HA 질문이 나오면

> "온프레미스에도 HA를 넣을 수 있습니다. VMware HA나 Patroni가 그 역할을 합니다.  
> 하지만 VMware HA는 물리 서버 여러 대 + 라이선스 비용, Patroni는 etcd 클러스터 + 복잡한 설정이 필요합니다.  
> EKS는 Karpenter(노드) + RDS Multi-AZ(DB) 설정 몇 줄로 동일한 효과를 냅니다.  
> **구축 비용, 운영 부담, 복구 속도 — 이 세 가지 차이가 실험의 포인트입니다.**"

## 8. EKS 전용 기능 — 온프레미스와 비교

> 우리 실험에서 직접 드러나는 것 3개 + 운영 편의성 차이 항목들.

---

### 핵심 3개 (실험에서 직접 보이는 것)

#### ① Karpenter — 노드 자동 확장 (시나리오 2·3)

```
부하 증가 → HPA가 파드 늘림 → 노드 자원 부족

온프레:  Pending 쌓임 → 사람이 노드 추가할 때까지 대기
EKS:     Karpenter가 감지 → EC2 노드 자동 생성 (60~90초) → Pending 해소
```

**온프레에서 동일하게 하려면:**
- Cluster Autoscaler + 물리 서버 여분 대기 (조달 리드타임 수 일~수 주)
- 또는 VMware / OpenStack 클러스터 별도 구축 (고비용·복잡)

**발표 포인트:** Karpenter는 NodePool + EC2NodeClass 설정 몇 줄. 온프레는 서버 구매부터 시작.

---

#### ② RDS Multi-AZ — DB 자동 페일오버 (시나리오 4, 선택)

```
Primary DB 죽음

온프레:  사람이 감지 → Replica에서 수동 승격 (pg_promote) → 앱 재연결 → 수 분
EKS:     RDS가 자동 감지 → Replica 자동 승격 → DNS 자동 전환 → 60초
```

**온프레에서 동일하게 하려면:**
- PostgreSQL Primary + Replica EC2 2대
- etcd 클러스터 3대 (홀수, 과반수 투표용)
- Patroni 설치·설정 (자동 승격 관리자)
- HAProxy 또는 VIP (앱이 항상 같은 엔드포인트로 연결)
- = EC2 5대 추가 + 수 주 구축 + 지속적 운영

**발표 포인트:** RDS는 콘솔에서 "Multi-AZ 활성화" 체크박스 하나. 온프레는 Patroni 생태계 전체를 직접 구축.

---

#### ③ 관리형 컨트롤 플레인 — 마스터 노드 AWS 관리

```
온프레:  마스터 노드 (API Server, etcd, Scheduler) 직접 운영
         - 마스터 죽으면 직접 복구
         - etcd 백업 직접
         - 버전 업그레이드 직접 (kubeadm upgrade)

EKS:     AWS가 마스터 노드 운영
         - 마스터 장애 자동 복구
         - etcd 자동 백업
         - 버전 업그레이드 클릭 한 번
```

**발표 포인트:** 우리 실험에서 마스터가 죽는 시나리오는 없지만, "운영 중 마스터 관리 부담"이 온프레의 현실적 비용.

---

### 운영 편의성 차이 (질문 나오면 묶어서 답할 것)

#### ④ AWS VPC CNI vs Flannel

| | 온프레 (Flannel) | EKS (VPC CNI) |
|---|---|---|
| 파드 IP | 가상 오버레이 대역 | **실제 VPC IP** |
| 통신 방식 | 패킷 한 번 더 감싸서 전송 | 네이티브 직접 통신 |
| 지연시간 | 약간 높음 (오버헤드) | 낮음 |
| 네트워크 정책 | Flannel 기본 | AWS Security Group 연동 |

> 우리 실험에서 이 차이는 직접 측정하지 않음. "CNI가 다른 것 자체가 각 환경 표준"으로 설명.

---

#### ⑤ IRSA (IAM Roles for Service Accounts)

```
EKS:   파드 → IAM 역할 자동 부여 → ECR pull, S3 접근 자동 인증
온프레: imagePullSecrets 수동 생성 + ECR 토큰 12시간마다 갱신 크론잡 필요
```

우리 프로젝트에서:
- EKS 워커노드 IAM Role → ECR 자동 인증
- 온프레 → `ghcr-secret` imagePullSecrets 수동 등록

---

#### ⑥ 관리형 노드 그룹 — OS 패치·업그레이드

```
온프레:  노드 OS 패치 직접 (apt upgrade)
         노드 교체: drain → 새 노드 설정 → join → 직접

EKS:     관리형 노드 그룹 → OS 보안 패치 자동
         노드 교체: drain → 새 노드 자동 → join 자동
```

---

### 전체 비교표

| 기능 | 온프레미스 | EKS | 실험 반영 |
|---|---|---|:---:|
| 파드 자동 확장 (HPA) | ✅ | ✅ | ✅ 양쪽 동일 |
| **노드 자동 확장** | ❌ | ✅ Karpenter | ✅ 시나리오 2·3 |
| **DB 자동 복구** | ❌ (Patroni 직접) | ✅ RDS Multi-AZ | ✅ 시나리오 4(선택) |
| **마스터 노드 관리** | 직접 | ✅ AWS 관리 | 간접적 |
| 네트워크 CNI | Flannel | VPC CNI | 측정 안 함 |
| 이미지 인증 | imagePullSecrets 수동 | IRSA 자동 | 셋업 차이 |
| OS 패치 | 직접 | 자동 | 운영 부담 차이 |
| 버전 업그레이드 | kubeadm 직접 | 콘솔 클릭 | 운영 부담 차이 |

---

### 발표에서 이 내용 쓰는 법

**직접 데이터로 보여주는 것 (필수):** Karpenter — 노드 확장 (시나리오 2·3)
**선택:** RDS Multi-AZ — DB 페일오버 (시나리오 4, 할지 미정)

**질문 나오면 말로 보완하는 것:**
