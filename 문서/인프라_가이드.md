## 1. 아키텍처 구조

```
AWS 단일 계정 (ap-northeast-2)
│
├── VPC-A (10.0.0.0/16) ─── 온프레미스 + 공통 인프라
│   └── Public 서브넷 10.0.1.0/24 (ap-northeast-2a)
│       │
│       ├── c8i.2xlarge  [EIP]  ← 온프레미스 k8s 호스트
│       │   ├── EC2 호스트 Nginx (:80 → VM NodePort 포워딩)
│       │   └── LXD (브릿지: lxdbr0)
│       │       ├── VM1 Master  <LXD_IP_1>  (Ubuntu 24.04, 2vCPU/4GB) k8s 컨트롤 플레인
│       │       ├── VM2 Worker1 <LXD_IP_2>  (Ubuntu 24.04, 2vCPU/4GB) ← traffic-node
│       │       └── VM3 Worker2 <LXD_IP_3>  (Ubuntu 24.04, 2vCPU/4GB) ← order-node
│       │       k8s v1.34.x (배포 확인됨), Flannel v0.26.7 CNI
│       │       ※ IP는 lxdbr0 대역 — lxc list로 확인
│       │
│       ├── t3.medium           ← PostgreSQL 16 (Docker, 10.0.2.112)
│       ├── t3.small            ← Redis 7 (Docker, 10.0.7.99)
│       ├── t3.small   [EIP]   ← Monitoring (Prometheus :9090 + Grafana :3000)
│       ├── t3.medium           ← k6-A (온프레미스 전용, EIP 불필요)
│       └── t3.medium  [EIP]   ← k6-B (EKS 전용, Worker Node NodePort 직접)
│
└── VPC-B (10.1.0.0/16) ─── EKS
    ├── Public 서브넷 10.1.1.0/24 (ap-northeast-2a)
    ├── Public 서브넷 10.1.2.0/24 (ap-northeast-2b)  ← EKS 최소 2 AZ
    ├── EKS Worker t3.medium (AZ-a) [EIP] ← traffic-node (실험 고정)
    │   └── API Gateway, Product, Inventory 파드
    ├── EKS Worker t3.medium (AZ-b) [EIP] ← order-node (실험 고정)
    │   └── Frontend, Order, Payment, User 파드
    ├── EKS Worker t3.medium               ← Karpenter 확장용 (실험 초기 idle)
    ├── k8s v1.34.x (확인됨)
    ├── RDS db.t3.medium       ← PostgreSQL 관리형
    └── t3.micro               ← Redis 7 (Docker)
```

**EIP가 필요한 이유:**

| EC2 | EIP | 이유 |
|---|:---:|---|
| c8i.2xlarge | 필수 | k6-A 타겟 고정, 재시작 시 IP 변동 방지 |
| Monitoring (t3.small) | 필수 | EKS Worker Node SG 인바운드 화이트리스트 등록 → 재시작 시 SG 재설정 방지 |
| k6-A | **불필요** | c8i.2xlarge SG가 k6-A SG 참조 방식으로 허용 → IP 기반 아님 |
| k6-B | 필수 | Worker Node SG 인바운드 화이트리스트에 고정 IP 등록 필요 |
| EKS Worker Node | 필수 | k6-B 직접 타겟 + Monitoring NodePort scrape |

## 2. Security Group 규칙

### SG 간 관계 한눈에

```
[인터넷]
    │ :80                                   │ :NodePort
    ▼                                       ▼
[k6-A SG]                         [k6-B SG]
    │ :80 (내부)                             │ :NodePort (공인IP, cross-VPC)
    ▼                                       ▼
[c8i.2xlarge SG]                    [Worker Node SG] ── (VPC-B)
    │ EC2 Nginx → VM NodePort               │
    ├─:5432→ [PostgreSQL SG]               ├─:5432→ [RDS SG]
    └─:6379→ [Redis-onprem SG]             └─:6379→ [Redis-EKS SG]

[Monitoring SG] ─── scrape ──→ [c8i.2xlarge SG]  (NodePort)
                            → [Worker Node SG]    (NodePort)
                            → [PostgreSQL SG]     (:9187)
                            → [Redis-onprem SG]   (:9121)
                            → [Redis-EKS SG]      (:9121)
```

## 3. 파드 고정 배치

### 배치 전략 (실제 배포 기준)

> **soft affinity (권고)** 로 운영 중. 부하 분산이 목적이 아닌 Pending 한계 실험이므로  
> 스케줄러가 자원 상황에 따라 자유 배치하도록 허용.

```
워커노드 1 (k8s-worker1)
┌────────────────────────────────────────────┐
│  API Gateway   :4000  (모든 트래픽 진입)   │
│  Product Svc   :4001  (Read, Redis 캐시)   │
│  Inventory Svc :4002  (SELECT FOR UPDATE)  │
└────────────────────────────────────────────┘

워커노드 2 (k8s-worker2)
┌────────────────────────────────────────────┐
│  Frontend      :3000  (정적, 부하 최소)    │
│  Order Svc     :4003  (Write, 주문 처리)   │
│  Payment Svc   :4004  (Write, 결제 처리)   │
│  User Svc      :4005  (로그인 처리)        │
└────────────────────────────────────────────┘

HPA 추가 파드 → 스케줄러 자유 배치 (soft affinity라 강제 아님)
  온프레미스: 양쪽 노드 꽉 참 → Pending 누적
  EKS:       Karpenter 신규 노드 추가 → Pending 해소
```

### 노드 라벨링

```bash
kubectl label node k8s-worker1 experiment-role=worker1
kubectl label node k8s-worker2 experiment-role=worker2
```

### nodeAffinity — soft (실제 적용값)

```yaml
affinity:
  nodeAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      preference:
        matchExpressions:
        - key: experiment-role
          operator: In
          values:
          - worker1   # 또는 worker2
```

> **soft affinity 이유:** `required`(강제)로 설정하면 HPA 스케일 시 해당 노드에 자원이 없을 경우  
> "자원 부족"인지 "affinity 조건 불충족"인지 구분이 안 돼 실험 결과 오염.  
> `preferred`(권고)로 설정하면 HPA 파드가 자유롭게 배치되어 Pending 발생 원인이 순수하게 "자원 부족"임을 증명.

### Resource Requests / Limits

HPA가 동작하려면 `resources.requests.cpu`가 반드시 있어야 한다.

| 서비스 | CPU Request | CPU Limit | Memory Request | Memory Limit |
|---|---|---|---|---|
| API Gateway | 150m | 1000m | 256Mi | 1Gi |
| Product Service | 100m | 500m | 128Mi | 512Mi |
| Inventory Service | 150m | 600m | 128Mi | 512Mi |
| Order Service | 100m | 500m | 128Mi | 512Mi |
| Payment Service | 100m | 500m | 128Mi | 512Mi |
| User Service | 100m | 500m | 128Mi | 512Mi |
| Frontend | 50m | 200m | 64Mi | 128Mi |

> 실제 값은 `msa_shoply/k8s/common/` 매니페스트 파일 기준.

### HPA 설정

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: <서비스명>-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: <서비스명>
  minReplicas: 1
  maxReplicas: 5
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60
```

| 서비스 | minReplicas | maxReplicas | targetCPU |
|---|:---:|:---:|:---:|
| API Gateway | 1 | **100** | 60% |
| Product Service | 1 | **100** | 60% |
| Inventory Service | 1 | **100** | 60% |
| Order Service | 1 | **100** | 60% |
| Payment Service | 1 | **100** | 60% |
| User Service | 1 | **100** | 60% |

> maxReplicas: **100** → 노드 한계 탐색 실험용. HPA가 파드를 계속 늘리려 시도 → Pending 누적 → 온프레미스 한계 명확히 드러남  
> scale-down cooldown: **60초** (기본 5분에서 단축 — 실험 후 빠른 정상화)  
> 실제 HPA는 `msa_shoply/k8s/common/hpa.yaml` 참고.

## 4. 트래픽 경로

ALB 없음. 양쪽 모두 **ingress-nginx + 80포트 진입**으로 통일 → 동일 조건.

### 온프레미스 트래픽 흐름 (KVM)

> KVM VM은 공인IP 없음(192.168.122.x) → EC2 호스트 Nginx가 NAT 중계

```
k6 (사설망)
    │ HTTP :80
    ▼
K8s EC2 호스트 (사설IP:80)
  [SG: k6 SG 인바운드 80 허용]
    │
  EC2 호스트 Nginx (proxy_pass)
    │ → master VM:30080
    ▼
master VM:30080 (ingress-nginx NodePort)
    ▼
ingress-nginx Controller Pod
    ├── /api/* → API Gateway Pod (:4000)
    │               ├── /api/products/*   → Product Service (:4001)
    │               ├── /api/inventory/*  → Inventory Service (:4002)
    │               ├── /api/orders/*     → Order Service (:4003)
    │               ├── /api/payments/*   → Payment Service (:4004)
    │               └── /api/auth/*       → User Service (:4005)
    └── /     → Frontend Pod (:80)
```

**EC2 호스트 Nginx 설정:**

```nginx
server {
    listen 80;
    location / {
        proxy_pass         http://<master-VM-IP>:30080;
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
    }
}
```

> KVM VM은 공인IP 없음 → EC2 호스트가 NAT 역할 (80 → master VM:30080)

### EKS 트래픽 흐름

> EKS 워커는 실제 EC2(공인IP) → NAT 중계 불필요. ingress-nginx를 hostPort 80으로 직접 노출.

```
k6
    │ HTTP :80
    ▼
EKS Worker Node (공인IP:80)
  [Worker Node SG: k6 EIP 인바운드 80 허용]
    │ ingress-nginx (hostPort 80)
    ▼
ingress-nginx Controller Pod
    ├── /api/* → API Gateway Pod (:4000)
    └── /     → Frontend Pod (:80)
```

### 온프레 vs EKS 진입 비교

| | 온프레미스 (KVM) | EKS |
|---|---|---|
| k6 타겟 | EC2 사설IP:80 | 워커 공인IP:80 |
| 80 받는 주체 | EC2 호스트 Nginx | ingress-nginx (hostPort) |
| VM/노드 전달 | Nginx proxy_pass → 30080 | 직접 (hostPort) |
| 중계 홉 | EC2 Nginx 1홉 추가 | 없음 |

### 서비스 타입 정리

| 서비스 | 타입 | 이유 |
|---|:---:|---|
| ingress-nginx | 온프레: NodePort 30080 / EKS: hostPort 80 | 외부 진입점 |
| API Gateway | ClusterIP | ingress가 내부 라우팅 |
| Frontend | ClusterIP | ingress가 내부 라우팅 |
| Product/Inventory/Order/Payment/User | ClusterIP | Gateway가 내부 라우팅 |
| 각 서비스 메트릭 (prom-client) | NodePort 30400~30404 | 외부 Prometheus scrape |

### 경로 비대칭 보정 (왜 이렇게 했는가)

온프레미스만 **EC2 호스트 Nginx 홉이 한 단계 더** 있다 (k6 → EC2:80 → VM:30080).
KVM VM에 공인IP가 없어 EC2가 NAT 역할을 해야 하는 **온프레미스의 구조적 특성**이다.
이 홉이 약간의 지연을 추가하므로:

> **응답시간은 절대값으로 직접 비교하지 않는다.**  
> 각 환경의 저부하 베이스라인을 기준점으로, 부하 증가에 따른 **상대적 악화율(%)** 을 비교한다.
> 홉 오버헤드는 베이스라인에 포함되어 상쇄 → 부하가 만드는 *변화*만 순수 비교된다.

## 7. 부하 테스트 & 노드 한계 탐색

### 서비스 성능 개선 내역

| 서비스 | 변경 내용 | 목적 |
|---|---|---|
| gateway | JWT 검증 미들웨어 + gzip 압축 (→ 추후 gzip 제거 예정) | CPU 사용량 증가 |
| payment | HMAC sha256 서명 + fetch timeout 10s | CPU 증가 + 타임아웃 방지 |
| product | LRU 인메모리 캐시 (max 600, 30s TTL) | 메모리 사용량 증가 |
| inventory | Redis DECRBY atomic 처리 | SELECT FOR UPDATE DB lock 경합 제거 |

### 서비스별 독립 스케일링을 위한 추가 개선 (B+C 방식)

**문제:** gateway만 CPU 높고 backend 6% → gateway만 스케일

**해결:**
- gateway: gzip 제거, JWT verify 후 헤더(`X-User-ID`)로 전달
- backend 5개: 자체 gzip + JWT verify 미들웨어 추가
- 결과: 각 서비스 독립적으로 CPU 증가 → 서비스별 HPA 트리거 → 개별 파드 증가

```
k6 → gateway(JWT verify) → payment(JWT verify #2 + gzip)
                          → product(JWT verify #2 + gzip + LRU)
                          → order(JWT verify #2 + gzip)
                          → inventory(JWT verify #2 + gzip + Redis)
```

### HPA가 트리거 안 되는 경우

**원인:** Node.js 서비스는 I/O 바운드 → 실제 CPU 사용량이 request보다 훨씬 낮음
```
파드 CPU request: 100m
실제 사용량: 10m
HPA 계산: 10/100 = 10% → 임계값(60%) 미달 → 스케일 안 함
```

**해결:**
```bash
# 1. HPA CPU 임계값 낮추기 (20%)
kubectl patch hpa payment-hpa -n shoply --type merge \
  -p '{"spec":{"metrics":[{"type":"Resource","resource":{"name":"cpu","target":{"type":"Utilization","averageUtilization":20}}}]}}'

# 2. maxReplicas 제한 없애기 (노드 실제 한계 찾기)
for hpa in gateway-hpa product-hpa inventory-hpa order-hpa payment-hpa; do
  lxc exec k8s-master -- kubectl patch hpa $hpa -n shoply \
    --type merge -p '{"spec":{"maxReplicas":100}}'
done
```

### k6 최대 부하 설정

sleep 완전 제거 + 웨이브당 200명 = **최대 2000명 동시 접속**

```bash
# 재고 리셋
docker exec shoply-postgres psql -U shoply -d shoply -c "

  '8d23364d-58e9-4c89-a216-1c7dfb1623c5',
```

### HPA scale-down 빠르게 하기 (실험용)

```bash

  lxc exec k8s-master -- kubectl patch hpa $hpa -n shoply \
```

## 8. 부하 테스트 트러블슈팅

### Gateway만 스케일되고 backend 서비스가 안 되는 경우

**증상:**
- gateway HPA만 트리거, payment/product/order/inventory CPU 6% 유지

**원인:**
- gateway에 gzip 압축이 있으면 gateway가 CPU를 독점
- backend 서비스는 단순 DB/Redis 조회 → Node.js I/O 바운드 → CPU 낮음
- gateway가 느려지면 뒷단으로 가는 처리량도 감소

**해결 (B+C 방식):**
- gateway: gzip 제거, JWT verify 후 헤더 전달
- backend 5개: 자체 gzip + JWT verify 미들웨어 추가
- 각 서비스가 독립적으로 CPU 사용 → 서비스별 HPA 트리거

---

### 결제 타임아웃 발생 (k6: request timeout)

**증상:**
```
Post "http://.../api/payments": request timeout
GoError: the body is null so we can't transform it to JSON
```

**원인:**
- payment → inventory(재고차감) → order(상태업데이트) 내부 호출 타임아웃
- SELECT FOR UPDATE 경합 또는 order 서비스 과부하 시 연쇄 지연

**해결:**
1. inventory Redis DECRBY 전환 (DB lock 경합 제거)
2. payment fetch timeout 추가 (`AbortSignal.timeout(10_000)`)
3. k6 check에서 null body 처리:
```javascript
'결제 처리됨': (r) => {
  try { return ['PAID', 'FAILED'].includes(r.json('status')); }
  catch { return false; }
}
```

---

### HPA가 트리거되지 않는 경우 (CPU 실사용량 낮음)

**증상:** 부하를 줘도 HPA TARGETS가 낮게 유지 (예: 6%)

**원인:**
- Node.js는 I/O 바운드 → DB 응답 기다리는 동안 CPU 거의 안 씀
- HPA는 실제 사용량/request 비율로 계산

**해결:**
- CPU request를 낮추거나 임계값 조정
- 서비스에 CPU 집약적 작업 추가 (JWT verify, gzip, HMAC)
