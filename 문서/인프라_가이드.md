## 1. 아키텍처 구조

```
AWS 단일 계정 (ap-northeast-2)
│
├── VPC-A (10.0.0.0/16) ─── 온프레미스 + 공통 인프라
│   └── Public 서브넷 10.0.1.0/24 (ap-northeast-2a)
│       │
│       ├── c8i.2xlarge  [EIP]  ← 온프레미스 k8s 호스트
│       │   ├── EC2 호스트 Nginx (:80 → VM NodePort 포워딩)
│       │   └── LXD (브릿지: lxdbr0)
│       │       ├── VM1 Master  <LXD_IP_1>  (Ubuntu 24.04, 2vCPU/4GB) k8s 컨트롤 플레인
│       │       ├── VM2 Worker1 <LXD_IP_2>  (Ubuntu 24.04, 2vCPU/4GB) ← traffic-node
│       │       └── VM3 Worker2 <LXD_IP_3>  (Ubuntu 24.04, 2vCPU/4GB) ← order-node
│       │       k8s v1.34.8 (배포 확인됨), Flannel v0.26.7 CNI
│       │       ※ IP는 lxdbr0 대역 — lxc list로 확인
│       │
│       ├── t3.medium           ← PostgreSQL 16 (Docker, 10.0.2.112)
│       ├── t3.small            ← Redis 7 (Docker, 10.0.7.99)
│       ├── t3.small   [EIP]   ← Monitoring (Prometheus :9090 + Grafana :3000)
│       ├── t3.medium           ← Locust-A (온프레미스 전용, EIP 불필요)
│       └── t3.medium  [EIP]   ← Locust-B (EKS 전용, Worker Node NodePort 직접)
│
└── VPC-B (10.1.0.0/16) ─── EKS
    ├── Public 서브넷 10.1.1.0/24 (ap-northeast-2a)
    ├── Public 서브넷 10.1.2.0/24 (ap-northeast-2b)  ← EKS 최소 2 AZ
    ├── EKS Worker t3.medium (AZ-a) [EIP] ← traffic-node (실험 고정)
    │   └── API Gateway, Product, Inventory 파드
    ├── EKS Worker t3.medium (AZ-b) [EIP] ← order-node (실험 고정)
    │   └── Frontend, Order, Payment, User 파드
    ├── EKS Worker t3.medium               ← Karpenter 확장용 (실험 초기 idle)
    ├── k8s v1.32.12 (확인됨)
    ├── RDS db.t3.medium       ← PostgreSQL 관리형
    └── t3.micro               ← Redis 7 (Docker)
```

**EIP가 필요한 이유:**

| EC2 | EIP | 이유 |
|---|:---:|---|
| c8i.2xlarge | 필수 | Locust-A 타겟 고정, 재시작 시 IP 변동 방지 |
| Monitoring (t3.small) | 필수 | EKS Worker Node SG 인바운드 화이트리스트 등록 → 재시작 시 SG 재설정 방지 |
| Locust-A | **불필요** | c8i.2xlarge SG가 Locust-A SG 참조 방식으로 허용 → IP 기반 아님 |
| Locust-B | 필수 | Worker Node SG 인바운드 화이트리스트에 고정 IP 등록 필요 |
| EKS Worker Node | 필수 | Locust-B 직접 타겟 + Monitoring NodePort scrape |

## 2. Security Group 규칙

### SG 간 관계 한눈에

```
[인터넷]
    │ :80                                   │ :NodePort
    ▼                                       ▼
[Locust-A SG]                         [Locust-B SG]
    │ :80 (내부)                             │ :NodePort (공인IP, cross-VPC)
    ▼                                       ▼
[c8i.2xlarge SG]                    [Worker Node SG] ── (VPC-B)
    │ EC2 Nginx → VM NodePort               │
    ├─:5432→ [PostgreSQL SG]               ├─:5432→ [RDS SG]
    └─:6379→ [Redis-onprem SG]             └─:6379→ [Redis-EKS SG]

[Monitoring SG] ─── scrape ──→ [c8i.2xlarge SG]  (NodePort)
                            → [Worker Node SG]    (NodePort)
                            → [PostgreSQL SG]     (:9187)
                            → [Redis-onprem SG]   (:9121)
                            → [Redis-EKS SG]      (:9121)
```

### VPC-A Security Groups

#### c8i.2xlarge SG

| 방향 | 포트 | 소스 | 이유 |
|---|---|---|---|
| 인바운드 | 80 | Locust-A SG | EC2 호스트 Nginx 부하 트래픽 수신 |
| 인바운드 | 22 | Admin IP/32 | SSH |
| 인바운드 | 6443 | Admin IP/32 | kubectl API Server |
| 인바운드 | 30000-32767 | Monitoring SG | Prometheus NodePort scrape |
| 아웃바운드 | 5432 | PostgreSQL SG | 파드 → DB |
| 아웃바운드 | 6379 | Redis-onprem SG | 파드 → Redis |
| 아웃바운드 | 443 | 0.0.0.0/0 | GHCR 이미지 풀 |

> 80을 Locust-A SG만 허용하는 이유: 실험 중 외부 직접 접근 차단 → 트래픽 오염 방지.

| 방향 | 포트 | 소스 | 이유 |

| 인바운드 | 9100 | Monitoring SG | Node Exporter scrape |
| 인바운드 | 22 | Admin IP/32 | SSH |
| 아웃바운드 | 전체 | 0.0.0.0/0 | — |

#### Redis-onprem SG (t3.small)

| 방향 | 포트 | 소스 | 이유 |
|---|---|---|---|
| 인바운드 | 6379 | c8i.2xlarge SG | Product Service 파드 → Redis |
| 인바운드 | 9121 | Monitoring SG | Redis Exporter scrape |
| 인바운드 | 9100 | Monitoring SG | Node Exporter scrape |

#### Monitoring SG (t3.small) — EIP 필수

| 방향 | 포트 | 소스/목적지 | 이유 |
|---|---|---|---|
| 인바운드 | 9090 | Admin IP/32 | Prometheus UI |

| 변경 항목 | 내용 |
|---|---|
| Worker Node SG 인바운드 | Monitoring EIP → 그대로 유지 (EIP는 계정 이동 후에도 동일) |

## 3. 파드 고정 배치

### 배치 전략

```
워커노드 1 (experiment-role: traffic-node)
┌────────────────────────────────────────────┐
│  API Gateway   :4000  (모든 트래픽 진입)   │
│  Product Svc   :4001  (Read 70%, 최고 RPS) │
│  Inventory Svc :4002  (SELECT FOR UPDATE)  │
│                                            │
│  [시나리오 2] 이 노드가 먼저 한계에 도달   │
└────────────────────────────────────────────┘

워커노드 2 (experiment-role: order-node)
┌────────────────────────────────────────────┐
│  Frontend      :3000  (정적, 부하 최소)    │
│  Order Svc     :4003  (Write, 20% RPS)     │
│  Payment Svc   :4004  (Write, 10% RPS)     │
│  User Svc      :4005  (로그인 1회, 최저)   │
│                                            │
│  [시나리오 4] 이 노드를 강제 종료          │
└────────────────────────────────────────────┘

HPA 추가 파드 → affinity 없음 → 스케줄러 자유 배치
  온프레미스: 양쪽 노드 꽉 참 → Pending 누적
  EKS:       Karpenter 신규 노드 추가 → Pending 해소
```

### 노드 라벨링

```bash
kubectl label node <worker-1-name> experiment-role=traffic-node
kubectl label node <worker-2-name> experiment-role=order-node
```

### nodeAffinity — 워커노드 1 고정 (API Gateway, Product, Inventory)

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: experiment-role
          operator: In
          values:
          - traffic-node
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels:
            app: <서비스명>
        topologyKey: kubernetes.io/hostname
```

### nodeAffinity — 워커노드 2 고정 (Frontend, Order, Payment, User)

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: experiment-role
          operator: In
          values:
          - order-node
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels:
            app: <서비스명>
        topologyKey: kubernetes.io/hostname
```

> `podAntiAffinity`를 `preferred`(권고)로 설정하는 이유:  
> `required`(강제)로 하면 온프레미스에서 HPA가 같은 서비스 파드를 추가할 노드를 못 찾아 Pending이 됨.  
> "자원 부족"인지 "안티어피니티 충돌"인지 구분이 안 돼 실험 결과 오염.

### Resource Requests / Limits

HPA가 동작하려면 `resources.requests.cpu`가 반드시 있어야 한다.

| 서비스 | CPU Request | CPU Limit | Memory Request | Memory Limit |
|---|---|---|---|---|
| API Gateway | 150m | 1000m | 256Mi | 1Gi |
| Product Service | 100m | 500m | 128Mi | 512Mi |
| Inventory Service | 150m | 600m | 128Mi | 512Mi |
| Order Service | 100m | 500m | 128Mi | 512Mi |
| Payment Service | 100m | 500m | 128Mi | 512Mi |
| User Service | 100m | 500m | 128Mi | 512Mi |
| Frontend | 50m | 200m | 64Mi | 128Mi |

> 실제 값은 `msa_shoply/k8s/common/` 매니페스트 파일 기준.

### HPA 설정

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: <서비스명>-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: <서비스명>
  minReplicas: 1
  maxReplicas: 5
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60
```

| 서비스 | minReplicas | maxReplicas | targetCPU |
|---|:---:|:---:|:---:|
| API Gateway | 2 | 5 | 60% |
| Product Service | 2 | 5 | 60% |
| Inventory Service | 2 | 5 | 60% |
| Order Service | 2 | 5 | 60% |
| Payment Service | 2 | 5 | 60% |

## 4. 트래픽 경로

ALB, MetalLB 없음. 양쪽 모두 **Nginx Ingress Controller (NodePort :30080)** 사용 → 동일 조건.

### 온프레미스 트래픽 흐름

```
Locust-A (VPC-A)
    │ HTTP :80
    ▼
c8i.2xlarge (공인IP:80)
  [SG: Locust-A SG 인바운드 허용]
    │
  EC2 호스트 Nginx (NAT 역할)
    │ proxy_pass → <VM2_LXD_IP>:30080
    ▼
kube-proxy (VM2 Worker1, traffic-node) :30080
    ▼
Nginx Ingress Controller Pod
    ├── /api/* → API Gateway Pod (:4000)
    │               ├── /api/products/*   → Product Service
    │               ├── /api/inventory/*  → Inventory Service
    │               ├── /api/orders/*     → Order Service
    │               ├── /api/payments/*   → Payment Service
    │               └── /api/auth/*       → User Service
    └── /     → Frontend Pod (:3000)
```

**EC2 호스트 Nginx 설정:**

```nginx
server {
    listen 80;
    location / {
        proxy_pass         http://<VM2_LXD_IP>:30080;
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
    }
}
```

> LXD VM은 공인IP 없음 → c8i.2xlarge가 NAT 역할.  
> `<VM2_LXD_IP>` = `lxc list k8s-worker1` 로 확인.

### EKS 트래픽 흐름

```
Locust-B (VPC-A, EIP 고정)
    │ HTTP :30080
    ▼
EKS Worker Node (공인IP:30080)
  [Worker Node SG: Locust-B EIP/32 인바운드 허용]
    │
  kube-proxy :30080
    ▼
Nginx Ingress Controller Pod
    ├── /api/* → API Gateway Pod (:4000)
    └── /     → Frontend Pod (:3000)
```

### 서비스 타입 정리

| 서비스 | 타입 | 이유 |
|---|:---:|---|
| Nginx Ingress Controller | NodePort :30080 | 외부 진입점 — Locust 타겟 |
| API Gateway | ClusterIP | Nginx Ingress가 내부 라우팅 |
| Frontend | ClusterIP | Nginx Ingress가 내부 라우팅 |
| Product / Inventory / Order / Payment / User | ClusterIP | API Gateway가 내부 라우팅 |
| 각 서비스 메트릭 (prom-client) | NodePort | 외부 Prometheus scrape |

## 6. LXD 트러블슈팅

### 1. KVM 미지원 (c8i-flex.2xlarge)

**증상:**
```bash
grep -c 'vmx\|svm' /proc/cpuinfo
# 결과: 0
```

**원인:** c8i-flex는 AWS Nitro 하이퍼바이저 — CPU 가상화 플래그(vmx/svm)를 게스트에 노출 안 함

**해결:** KVM 대신 **LXD 컨테이너**로 대체 (커널 네임스페이스 기반, CPU 가상화 불필요)

---

### 2. snap store 연결 불가

**증상:** `unable to contact snap store`

**원인:** EC2에 퍼블릭 IP 미할당 → 퍼블릭 서브넷이어도 인터넷 접근 불가

**해결:** AWS 콘솔에서 Elastic IP 할당 또는 퍼블릭 IP 자동 할당 활성화

---

### 3. apt 캐시 공간 부족

**증상:**
```
E: You don't have enough free space in /var/cache/apt/archives/.
```

**원인:** LXD 컨테이너 루트 파티션이 꽉 참 (7GB)

**해결:**
```bash
# 1단계: apt 캐시 정리
for node in k8s-master k8s-worker1 k8s-worker2; do
  lxc exec $node -- apt clean
done

# 2단계: EC2 루트 파티션 확장 (EBS 볼륨 확장 후)
sudo growpart /dev/nvme0n1 1
sudo resize2fs /dev/nvme0n1p1
df -h /
```

### 4. hold 패키지 재설치 오류

**증상:**
```
E: Held packages were changed and -y was used without --allow-change-held-packages.
```

**해결:**
```bash

  kubeadm=1.32.12-1.1 kubelet=1.32.12-1.1 kubectl=1.32.12-1.1
```

### 6. kube-proxy CrashLoopBackOff (conntrack permission denied)

**증상:**
```
E: "Error running ProxyServer" err="open /proc/sys/net/netfilter/nf_conntrack_max: permission denied"
```
- kube-proxy 3개 노드 모두 CrashLoopBackOff
- Flannel이 API 서버 접근 불가 → CrashLoopBackOff
- CoreDNS ContainerCreating 상태에서 멈춤

**원인:** LXD 컨테이너에서 netfilter sysctl은 공유 커널 네임스페이스 → 쓰기 권한 없음  
kube-proxy 실패 → iptables 규칙 미설정 → ClusterIP 라우팅 불가 → Flannel API 서버 접근 불가

**해결:** kube-proxy ConfigMap에서 conntrack max 설정을 `0`으로 패치

```bash
lxc exec k8s-master -- bash -c "
  kubectl -n kube-system get cm kube-proxy -o json | \
  sed 's/maxPerCore: null/maxPerCore: 0/' | \
  kubectl apply -f -
"

lxc exec k8s-master -- kubectl -n kube-system rollout restart daemonset kube-proxy
lxc exec k8s-master -- kubectl -n kube-flannel rollout restart daemonset kube-flannel-ds
```

### 서비스 성능 개선 내역

| 서비스 | 변경 내용 | 목적 |
|---|---|---|

### HPA가 트리거 안 되는 경우

**원인:** Node.js 서비스는 I/O 바운드 → 실제 CPU 사용량이 request보다 훨씬 낮음
```
파드 CPU request: 100m
실제 사용량: 10m
HPA 계산: 10/100 = 10% → 임계값(60%) 미달 → 스케일 안 함
```

**해결:**
```bash
# 1. HPA CPU 임계값 낮추기 (20%)
kubectl patch hpa payment-hpa -n shoply --type merge \
  -p '{"spec":{"metrics":[{"type":"Resource","resource":{"name":"cpu","target":{"type":"Utilization","averageUtilization":20}}}]}}'

# 2. maxReplicas 제한 없애기 (노드 실제 한계 찾기)
for hpa in gateway-hpa product-hpa inventory-hpa order-hpa payment-hpa; do
  lxc exec k8s-master -- kubectl patch hpa $hpa -n shoply \
    --type merge -p '{"spec":{"maxReplicas":100}}'
done
```
