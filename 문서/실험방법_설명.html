온프레미스 vs EKS 비교 실험

왜 "부하코드"가 아니라 "request 튜닝"으로 실험하는가 — 끝까지 읽으면 이해됨

0먼저 — 우리가 도대체 뭘 보려는 거야?

이 실험의 결론은 딱 한 문장이야:

트래픽이 폭증하면 —
🖥️ 온프레미스는 노드가 고정이라 더 못 버티고 터진다(Pending)
☁️ EKS는 노드를 자동으로 늘려서 계속 버틴다(Karpenter)

이 차이를 그래프로 증명하는 게 목표야. 그러려면 "파드가 자동으로 늘어나는 상황"(HPA)을 만들어야 해. 안 그러면 둘 다 멀쩡해서 비교할 게 없어.

여기서 문제가 생겨 👉 우리 앱은 너무 가벼워서, 부하를 줘도 파드가 안 늘어나. 그래서 "어떻게 파드를 늘릴 거냐"를 두고 두 가지 길이 있는 거야.

1request가 도대체 뭐야? (식당 비유)

k8s에서 request는 "파드 한 개가 노드에서 미리 예약하는 CPU 자리"야. 상품 개수랑 전혀 상관없어. 그냥 설정 숫자야.

🍽️ 식당으로 생각하면

실제 k8s식당 비유
노드(워커 서버)식당 — 총 좌석 2000석 (=2 vCPU)
파드(우리 서비스)손님 — 입장할 때 좌석을 예약(request)함
request: 100m손님 1명이 100석 예약
파드가 더 못 들어감 = Pending좌석 다 차서 "자리 없음"

핵심: 손님 1명이 예약하는 좌석(request)을 작게 잡을지 크게 잡을지를 우리가 정한다는 거야. 이게 "request 튜닝".

2직접 움직여봐 👇 (이게 핵심)

슬라이더 2개를 움직이면서 노드에 파드가 어떻게 차는지 봐. 빨간 파드 = Pending(자리없음).

온프레미스 워커노드 (고정, 2000m)
EKS 워커노드 (Karpenter 자동 확장)

💡 실험해볼 것:

  • request를 작게(50m) → 파드가 많이 들어가지만, HPA가 워낙 민감해서 금방 30개까지 늘어남 → 결국 노드 꽉 참
  • 파드 개수를 30개로 → 온프레는 빨강(Pending) 폭발, EKS는 노드를 늘려서 다 초록
  • 이 "온프레 빨강 vs EKS 초록"이 바로 우리가 발표에서 보여줄 그림이야

3그래서 "파드를 늘리는" 두 가지 방법

파드는 HPA가 늘려. HPA 공식은 이거 하나야:

늘릴까 말까? =  지금 쓰는 CPU  ÷  예약한 CPU(request)

  예) 파드가 실제 60m 쓰는 중
      request 100m → 60 ÷ 100 = 60% → "늘려!" ✅
      request 500m → 60 ÷ 500 = 12% → "안 늘려" ❌ (잠잠)

파드를 늘리려면 이 비율(%)을 높여야 해. 방법이 두 개야:

방법뭘 바꾸나분자/분모 어디를?
🔴 부하코드 앱 코드에 CPU 태우는 로직 추가 → 실제 사용 CPU(분자)를 키움 분자 ↑ (60m→300m)
🟢 request 튜닝 yaml 숫자만 줄임 → 예약 CPU(분모)를 작게 분모 ↓ (500m→100m)

둘 다 비율(%)을 높여서 HPA를 발동시켜. 목적지는 같은데 가는 길이 달라.

4왜 우리는 request로 가는가 (결정 이유)

🔴 부하코드 (안 감)

  • 이미 해봤고 망함 — gateway만 터지고 나머지 안 늘어남 (서비스마다 무게 달라서)
  • 고칠 때마다 코드 재빌드 + 이미지 재배포 → 실험 직전에 시간 다 날림
  • "왜 인위 부하 넣었냐" 멘토 질문 방어 어려움
  • 방금 우리가 깨끗하게 다 지운 걸 되돌리는 셈

🟢 request 튜닝 (감 ✅)

  • yaml 숫자 한 줄 — kubectl apply로 즉시 적용
  • 양쪽 환경 완전히 똑같이 적용 → 공정성 완벽
  • "k8s는 원래 request로 스케줄링한다" → 방어 끝 (실무 그대로)
  • 코드는 깨끗한 채로 유지

✅ 결론: 우리 실험 목적은 "노드가 늘어나냐 마냐(HPA→Pending vs Karpenter)"야. 이건 request 튜닝이 정확히 보여주는 그림이고, 부하코드는 했다가 실패한 길. 그래서 request로 간다.

그럼 "하이브리드"는 뭐였어?

걱정 하나가 남아: "request만 줄이면 실제 CPU는 낮아서, 대시보드 CPU 패널이 밋밋하지 않나?"
→ 그래서 RPS(부하량)를 크게 줘. 그러면 실제 CPU도 어느 정도 같이 올라와서 CPU 패널도 안 밋밋해. 이게 하이브리드야 — 부하"코드"가 아니라 부하"량"으로 CPU를 올리는 것.

다이얼 1 (메인) : request 작게  → HPA 확실히 발동
다이얼 2 (보조) : RPS 크게      → 실제 CPU도 올림 (패널 안 밋밋)
다이얼 3 (최후) : 부하코드       → 리허설에서 정말 안 되면 (아마 안 씀)

5그래서 시나리오는? (3개)

안정 → 스파이크 → 장애 순서로. 신뢰 형성 → 갈림 → 임팩트.

🅰️ 시나리오 1 — 안정 (베이스라인)

10~20분
200 RPS 일정 — 양쪽 다 정상 (Error 0, Pending 0)

결론 문장: "평상시엔 온프레미스도 충분합니다" (공정성 어필 → 신뢰 형성)

🅱️ 시나리오 2 — 스파이크 (순간 급증 + 유지) ★핵심

0~5분
200 RPS — 안정
5분 ⚡
1500 RPS로 순간 급증 (30초~1분에 걸쳐)
5~15분
1500 RPS 유지 ← 진짜 실험. 온프레 Pending 지속 / EKS Karpenter 노드추가(60~90초) 후 회복

⚠️ 유지가 핵심: 급증만 하고 빼면 시스템 반응 전에 끝나 안 보임. 급증 후 5~10분 유지해야 차이가 드러남.

결론 문장: "갑자기 몰리면 — EKS는 흡수하고, 온프레는 계속 무너집니다"

🅲 시나리오 3 — 노드 장애 복구 (MTTR)

0~5분
500 RPS 일정 — 양쪽 안정
5분 ⚡
worker1 강제 종료 → 모든 파드가 worker2로 몰림 → 자원 부족 Pending
측정
온프레 수동복구 수 분 / EKS Karpenter 자동 60초 — MTTR + 결제 실패 건수

결론 문장: "복구 시간이 곧 비즈니스 손실 — N분 vs 60초"
