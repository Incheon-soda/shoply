# 온프레미스 vs EKS 비교 실험 — 마스터 가이드

> 이 문서 하나로 **"무엇을·왜·어떻게"** 가 다 정리된다.
> 흩어진 결정·설정·시나리오·측정을 전부 여기 모았다.

---

## 0. 실험 프레임 — 무엇을 비교하는가 ★

이 실험은 *"어느 환경이 더 빠른가"* 가 아니라,
**"고정 자원의 한계(온프레미스) vs 탄력적 노드 확장(EKS)이 만드는 운영 특성 차이"** 를 측정한다.

| | 온프레미스 | EKS |
|---|---|---|
| 파드 확장 | HPA (동일) | HPA (동일) |
| **노드 확장** | **없음 (고정)** | **Karpenter (자동)** ← 독립변수 |
| 결과 | 자원 소진 → **Pending 누적** → Error↑ | 노드 추가 → Pending 해소 → 유지 |

> **→ 온프레미스에서 Pending이 쌓이고 Error가 오르는 것은 "패배"가 아니라 측정 대상 그 자체다.**
> 멘토 질문 *"노드를 못 늘려서 진 것 아니냐"* 의 답: **노드 확장 유무가 곧 독립변수**다.
> 그래서 온프레미스에 의도적으로 추가 노드 여력을 주지 않는다.

## 1. 부하 생성 방식 — 하이브리드 ★

깨끗한 Node.js 앱은 너무 가벼워서 부하를 줘도 HPA가 안 도는 함정이 있다. 해결:

| 다이얼 | 방법 | 역할 |
|:---:|---|---|
| **1차 (메인)** | `request: 100m` 작게 + HPA target 60% | HPA 확실히 발동 |
| **2차 (보조)** | k6 RPS 크게 | 실제 CPU도 올려 대시보드 그림 살림 |
| 3차 (최후) | 균등 연산 주입 | 리허설에서 정말 안 될 때만 (현재 미사용) |

> **부하 "코드"가 아니라 부하 "량"으로 CPU를 올린다.** 코드는 깨끗한 상태 유지.
> request를 작게 잡으면 `실제CPU÷request`(HPA 공식)가 쉽게 60%를 넘어 파드를 팍팍 늘린다 →
> 노드가 빨리 차서 온프레 Pending vs EKS 노드추가 대비가 선명해진다.
> (과거 JWT/bcrypt/LRU 부하코드는 gateway 편중·재빌드 지옥으로 전부 제거함)

## 2. 확정 설정값 ★

### 리소스 (HPA 민감하게 — 양쪽 동일)

| 서비스 | request | limit | HPA target | max replicas |
|---|:---:|:---:|:---:|:---:|
| gateway | 100m | 500m | 60% | 6 |
| product | 100m | 500m | 60% | 10 |
| inventory | 100m | 500m | 60% | 10 |
| order | 100m | 500m | 60% | 8 |
| payment | 100m | 500m | 60% | 8 |
| user | 100m | 500m | (HPA 없음) | — |
| frontend | 50m | 200m | (HPA 없음, 정적) | — |

### DB 커넥션

| 항목 | 값 | 이유 |
|---|:---:|---|
| 앱 pool max | **8** (전 서비스 통일) | 파드 다수 × 8 ≤ PG 한계 |
| PostgreSQL `max_connections` | **300** | 곱셈 폭증 대비 |
| `connectionTimeoutMillis` | 5000 | DB 페일오버 시 죽은 Primary 빠르게 포기 |
| `keepAlive` | true | 끊긴 연결 빠르게 감지 |

### 파드 배치 (soft nodeAffinity — 초기 고정, 추가분 자유)

| 노드 라벨 | 서비스 |
|---|---|
| `experiment-role=worker1` | gateway, product, inventory |
| `experiment-role=worker2` | frontend, order, payment, user |

> 초기 파드는 지정 워커에, HPA 추가 파드는 노드 꽉 차면 자유 배치.
> **배포 시 노드 라벨링 필수**: `kubectl label node <워커> experiment-role=worker1`

|---|---|
| 상품 | **456종** × 7사이즈(240~300) = 3,192 SKU |
| 재고 | 평균 289 (실험 전 `load-test-prep.sql`로 바닥값 500 확보) |

## 3. EKS vs 온프레미스 대응표

| 컴포넌트 | EKS | 온프레미스 | 일치 | 비고 |
|---|---|---|---|---|
| K8s 버전 | (확인 후 맞춤) | **1.34.x** | 반드시 동일 | ⚠️ EKS 버전 확정 필요 |
| 컨테이너 런타임 | containerd | containerd | 동작 동일 | |
| CNI | AWS VPC CNI | Flannel | 다름 (의도) | 각 환경 표준 |
| 노드 OS | AL2023 | Ubuntu 24.04 | 다름 | |
| 노드 스펙 | t3.medium 2c/4GB | LXD 컨테이너 2c/4GB | 동일 스펙 | 공정 비교 |
| **노드 확장** | **Karpenter** | **없음** | 다름 | **실험 핵심** |
| Ingress | **ingress-nginx + NodePort** | ingress-nginx + NodePort | ✅ 동일 | LB는 통제 변수로 통일 |
| DB | RDS PostgreSQL 16 | EC2 Docker PG 16 | 엔진 동일 | HA 방식 다름 |
| Redis | EC2 Docker 7 | EC2 Docker 7 | 동일 | 통제 변수 |
| 서비스 이미지 | **GHCR 동일 이미지** | **GHCR 동일 이미지** | 완전 동일 | 단일 레지스트리 |
| 노드 모니터링 | node_exporter | LXD 메트릭 | 측정 방식 다름 | |

> **이미지는 GHCR 단일 레지스트리** — 양쪽이 같은 이미지를 pull (ECR 미사용).
> 실험 시 `:latest` 금지, **커밋 SHA 태그로 고정**해야 100% 동일 보장.

## 4. 실험 시나리오 — A / B / C ★

> 현재 k6(`scenario.js`)는 **"파드가 실제로 늘어나는지" 검증용**. 본 실험용 A/B/C 스크립트는 별도 작성(리허설 전).

### 🅰️ 시나리오 A — 한계 측정 (계단식 부하)

```
100 → 300 → 1000 → 1500 RPS 단계적 증가 (각 2~4분) → 1500 유지
```
- **목적:** "몇 RPS에서 온프레 한계인가" 특정
- **온프레:** 특정 RPS에서 HPA 한계 → Pending 누적 → Error↑
- **EKS:** Karpenter 노드 추가 → 계속 감당
- **킬러 패널:** Pending Pod / Node Count / HPA desired-vs-current / Error율
- **트래픽:** 인프라 한계 측정 → 고정 토큰 권장 (로그인 변수 제거)

### 🅱️ 시나리오 B — 노드 장애 복구 (MTTR)

```
500 RPS 일정 → 5분 후 워커노드2 강제 종료 (drain or EC2 stop)
```
- **워커2 종료 시:** order/payment/user 죽음, product/gateway(워커1) 생존 → "상품은 보이는데 주문이 안 됨"
- **온프레:** 갈 노드 없음 → 복구 지연 (수 분)
- **EKS:** Karpenter 새 노드 → 자동 복구 (30~60초)
- **킬러 패널:** Error율 회복 시간(MTTR) / 결제 실패 건수
- **트래픽:** 현실 흐름 (현재 k6 — 로그인 포함)

### 🅲 시나리오 C — DB 페일오버 (MTTR)

```
500 RPS 일정 → Primary DB 강제 종료 → Replica 승격 / RDS 자동 페일오버
```
- **온프레:** Primary-Replica 스트리밍 복제 → **수동 승격**(`pg_promote`) 수 분
- **EKS:** RDS Multi-AZ → **자동 페일오버** 60~120초
- **킬러 패널:** DB Up/Down(pg_up) MTTR / Replication Lag / DB 연결 실패
- **앱 대응:** `connectionTimeoutMillis 5000` + `keepAlive`로 새 Primary 빠르게 재연결

## 5. 비교 지표 + PromQL

| # | 지표 | PromQL | 시나리오 |
|:---:|---|---|:---:|
| 1 | 전체 RPS | `sum(rate(gateway_http_duration_seconds_count{route!~"/health\|/metrics"}[1m]))` | A |
| 2 | P95 응답시간 | `histogram_quantile(0.95, rate(gateway_http_duration_seconds_bucket[1m]))` | A·B |
| 3 | 결제 성공률 | `sum(rate(payment_processed_total{status="PAID"}[2m])) / (PAID+FAILED) * 100` | B·C |
| 4 ★ | **Pending Pod** | `count(kube_pod_status_phase{namespace="shoply",phase="Pending"}) or on() vector(0)` | A |
| 5 | HPA desired vs current | `kube_horizontalpodautoscaler_status_{desired,current}_replicas{namespace="shoply"}` | A |
| 6 | 워커 CPU | `sum by(name)(rate(lxd_cpu_seconds_total{name=~"k8s-worker.*"}[1m])) / sum by(name)(lxd_cpu_effective_total{...}) * 100` | A |
| 7 | DB 활성 커넥션 | `pg_stat_activity_count{state="active"}` (max **300** 기준) | A |
| 8 | 파드 수 | `kube_deployment_status_replicas_available{namespace="shoply"}` | A·B |
| 9 ★ | **DB Up/Down (MTTR)** | `pg_up{job="postgres-onprem"}` | C |
| 10 | Replication Lag | `pg_replication_lag_seconds{job="postgres-onprem"}` | C |

## 6. 실험 절차

```
1. 리허설 — 시나리오 A를 500 RPS로 1회 → HPA 발동·CPU 관찰 → request/RPS 다이얼 확정
2. 양쪽 DB 리셋 (load-test-prep.sql) + Redis FLUSH + 파드 정상 확인
3. 시나리오 A 동시 시작 (온프레·EKS 같은 시각) → Grafana 기록 + 스냅샷
4. DB 리셋 후 시나리오 B (노드 종료 → MTTR)
5. DB 리셋 후 시나리오 C (DB 페일오버 → MTTR)
6. 수치 정리 → 발표 자료 (한계 RPS / MTTR 비교)
```

### 실험 전 체크리스트

```bash
# 1. DB 리셋 (양쪽 동일)
docker exec msa_postgres psql -U shoply -d shoply -f /db/load-test-prep.sql
#   → 재고 바닥값 500 확보 + reserved 0 + 거래내역 초기화

# 2. 파드 정상
kubectl get pods -n shoply

# 3. HPA 확인
kubectl get hpa -n shoply

# 4. Prometheus 타겟 up
curl -s http://localhost:9090/api/v1/targets | grep -o '"health":"[a-z]*"' | sort | uniq -c
```
