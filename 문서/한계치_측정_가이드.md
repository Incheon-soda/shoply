# 온프레미스 한계치 측정 가이드

> 부하를 점점 올리면서 "온프레미스가 몇 RPS/VU에서 무너지는지" 찾는 실전 방법.
> 이 숫자가 발표의 핵심 — "온프레미스 한계 = N RPS".

---

## 1. 한계의 정의

**한계 = Pending Pod이 처음 뜨는 지점.**

```
부하 증가 → HPA가 파드 늘림 → 노드 자원 소진
→ HPA는 더 늘리고 싶은데 노드에 자리 없음
→ Pending 발생  ← 여기가 한계 ★
```

> "HPA는 늘리려는데 못 늘린다" = 고정 자원의 한계. 이게 EKS(Karpenter로 노드 추가)와 갈리는 지점.

---

## 2. 한계 도달 신호 3가지

| 신호 | 확인 명령 | 한계? |
|---|---|---|
| Pending 발생 | `kubectl get pods -n shoply --field-selector=status.phase=Pending` | ★ **한계 도달** |
| 워커 CPU 90%+ | `kubectl top nodes` | 거의 다 참 |
| HPA CURRENT = MAX | `kubectl get hpa -n shoply` | 더 못 늘림 |

**Pending이 가장 명확한 신호.** 나머지 둘은 보조.

---

## 3. 측정 방법 — 계단식으로 올리기

한 번에 확 올리지 말고, **단계별로 찍으면서** 올린다.

```
500 VU   → [확인] → CPU? Pending? 파드 수?
1000 VU  → [확인]
2000 VU  → [확인]
4000 VU  → [확인]
...
Pending 뜨는 지점 = 한계
```

### 매 단계 확인 (3개 한 번에)

```bash
# 상태별 파드 수 (Running 몇 개 / Pending 몇 개)
kubectl get pods -n shoply --no-headers | awk '{print $3}' | sort | uniq -c

# 워커 노드 CPU
kubectl top nodes

# HPA 현재 vs 목표
kubectl get hpa -n shoply
```

### Pending만 빠르게

```bash
# Pending 개수
kubectl get pods -n shoply --field-selector=status.phase=Pending --no-headers | wc -l

# NODE가 <none>이면 배치 안 된 것 = Pending
kubectl get pods -n shoply -o wide
```

---

## 4. 역산 — 대략의 한계 예측

선형이라고 가정하면 현재 상태에서 한계를 추정할 수 있다.

```
예) 2000 VU에서 노드 50% 참 (파드 ~20개)
    → 4000 VU에서 100% → Pending 시작 예상

계산: 노드 2개 × 2core = 4000m
      request 100m → 노드당 ~20개 파드
      2노드 = ~40개에서 노드 꽉 참 → Pending
      (시스템 파드 자리 빼면 실제 35~38개)
```

> 선형이 아닐 수 있음(캐시·DB 병목). 역산은 출발점일 뿐, **실제 Pending 뜰 때까지 올려서 확인.**

---

## 5. 부하 올리는 두 가지 방법

| 방법 | 무엇 | 발표 설명 |
|---|---|---|
| **동시 접속자(VU) 늘리기** | "사람 수" 증가 | ✅ "N명이 동시에 몰리면" — 직관적 |
| 텀(wait) 줄이기 | 1인당 요청 빈도 증가 | 보조 |

둘 다 결국 RPS를 올려 CPU를 더 태우는 것. **VU 늘리기가 설명하기 쉬움.**

### k6 웨이브 늘리는 예시

```js
// 지금: 10웨이브 × 200 = 2000명
// 방법 A — 웨이브 추가 (20웨이브 × 200 = 4000명)
// 방법 B — 웨이브당 인원 키우기 (10웨이브 × 400 = 4000명)
```

---

## 6. Pending 원인 검증 (중요)

Pending이 떴으면 **"노드 자원 부족"이 진짜 원인인지** 확인한다.

```bash
kubectl describe pod <pending-파드명> -n shoply | grep -A3 Events
```

| Events 메시지 | 의미 |
|---|---|
| `Insufficient cpu` / `Insufficient memory` | ✅ **정답** — 노드 자원 부족 (원하던 그림) |
| `ImagePullBackOff` | ❌ 이미지 못 받음 (다른 문제) |
| `node affinity` 충돌 | ❌ 배치 규칙 문제 (다른 문제) |

→ `Insufficient`가 나와야 "고정 자원 한계"로 측정이 유효하다.

---

## 7. 기록 템플릿

Pending 뜨는 순간, **같은 시점**의 값을 기록한다 (Grafana 패널 + kubectl).

| 측정 | 값 | 출처 |
|---|---|---|
| 한계 VU | ___ 명 | k6 |
| 한계 RPS | ___ RPS | Grafana 전체 RPS |
| 그때 Running 파드 | ___ 개 | `uniq -c` |
| 그때 Pending 파드 | ___ 개 | `uniq -c` |
| 그때 워커 CPU | ___ % | `top nodes` |
| 그때 Error율 | ___ % | Grafana k6 실패율 |

→ 완성 문장:
> **"온프레미스는 N RPS(M명)에서 Pending P개 발생, Error율 X%로 한계 도달"**

---

## 8. 측정 흐름 요약

```
1. load-test-prep.sql 실행 (재고/주문 리셋)
2. Grafana 대시보드 띄움 (파드 상태 패널 주목)
3. k6 부하 시작 — 낮은 VU부터
4. 계단식으로 VU 올리며 매 단계 확인
5. Pending 뜨는 지점 발견 → 그 순간 값 전부 기록
6. describe로 Pending 원인이 Insufficient인지 검증
7. 기록 템플릿 채움 → 시나리오 A 데이터 확보
```

---

## 참고 — 한계가 안 보일 때

| 증상 | 원인 | 조치 |
|---|---|---|
| CPU 낮은데 파드 안 늠 | 부하 약함 | VU 더 올림 |
| 파드 느는데 Pending 안 뜸 | 노드 여유 있음 | VU 더 올림 (한계까지) |
| k6가 목표 RPS 못 만듦 | 부하 생성기 한계 | k6 서버 스펙 ↑ or 분산 |
| Pending 원인이 Insufficient 아님 | 설정 문제 | 이미지/affinity 점검 |
