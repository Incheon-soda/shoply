### 1-1. VPC 설계 — 몇 개? 어떻게?

> ✅ **결정: 단일 계정 우선, 크레딧 부족 시 2계정으로 전환**

**기본 구조: 단일 계정 + VPC 2개**

```
단일 AWS 계정

VPC-A (10.0.0.0/16) — 온프레미스 + 공통
└── Public 서브넷 (10.0.1.0/24) — ap-northeast-2a
    ├── c8i.2xlarge   (k8s 호스트 + LXD)
    ├── t3.medium     (PostgreSQL)
    ├── t3.micro      (Redis)
    ├── t3.small      (Monitoring — Prometheus + Grafana)
    └── t3.medium     (Locust)

VPC-B (10.1.0.0/16) — EKS
├── Public 서브넷 ap-northeast-2a  (10.1.1.0/24)
├── Public 서브넷 ap-northeast-2b  (10.1.2.0/24)  ← EKS 최소 2개 AZ 필요
├── EKS 워커노드 t3.medium × 3 (2 고정 + 1 Karpenter 확장용)
├── RDS db.t3.medium
└── t3.micro (Redis)
```

**Prometheus scrape 전략 (VPC 구분 없이 동작하도록):**  
처음부터 Public IP + NodePort로 설계 → 나중에 2계정으로 분리해도 scrape 설정 변경 없음

```
Monitoring EC2 (VPC-A)
  ├── 온프레미스 k8s: c8i.2xlarge 공인IP:NodePort  (VPC 내부 → 사설IP 사용 가능)
  ├── EKS 워커노드:   공인IP:NodePort               (VPC-B → 공인IP 경유)
  ├── PostgreSQL:    VPC-A 사설IP:9187
  └── Redis × 2:    각각 사설IP or 공인IP:9121
```

**2계정 전환 시 바뀌는 것 (최소화):**
- Monitoring EC2 EIP를 EKS 워커노드 SG에 추가 등록
- ECR 각 계정에 따로 push (GitHub Actions credentials 추가)
- 그 외 scrape 설정, k8s yaml은 그대로

### 1-2. Prometheus 아키텍처

> ✅ **결정: 계정 구조 무관하게 Prometheus 1개 (VPC-A t3.small)**

```
Monitoring EC2 (VPC-A, t3.small, EIP 고정)
  │
  ├── 온프레미스 scrape
  │     ├── kube-state-metrics   c8i.2xlarge 사설IP:NodePort   (단일계정 내부)
  │     ├── prom-client 각 서비스 c8i.2xlarge 사설IP:NodePort
  │     ├── PostgreSQL Exporter  t3.medium 사설IP:9187
  │     ├── Redis Exporter       t3.micro  사설IP:9121
  │     └── Node Exporter        VM 192.168.122.2~4:9100
  │           ↑ 단일계정: 사설IP / 2계정: 공인IP로 변경
  │
  └── EKS scrape
        ├── kube-state-metrics   EKS Worker Node 공인IP:NodePort
        ├── prom-client 각 서비스 EKS Worker Node 공인IP:NodePort
        ├── postgresql_exporter  EKS 내부 k8s Pod → Worker Node 공인IP:NodePort
        ├── Redis Exporter       EKS Redis EC2 공인IP:9121
        └── Node Exporter        EKS Worker Node 공인IP:9100

Grafana (같은 t3.small, 포트 3001)
  └── DataSource: Prometheus 1개
      └── 온프레미스 | EKS 패널 나란히 → 동일 타임라인 비교
```

**EKS postgresql_exporter 배포 방식:**  
RDS는 VPC-B 내부에서만 접근 가능 → exporter를 k8s Pod로 배포 → NodePort로 노출 → Prometheus scrape

**2계정 전환 시 변경:**  
온프레미스 scrape 대상 IP를 사설IP → 공인IP로 변경, Monitoring EIP는 그대로

### 1-3. Locust 배치

> ✅ **결정: 계정 구조 무관하게 Locust 2대 (각 환경 전용)**

```
Locust-A (VPC-A, t3.medium, EIP)  → 온프레미스 LB 전용
  타겟: http://<c8i.2xlarge-사설IP>:80   (단일계정: 내부)
        http://<c8i.2xlarge-공인IP>:80   (2계정: 외부)

Locust-B (VPC-A, t3.medium, EIP)  → EKS ALB 전용
  타겟: http://<ALB-DNS>:80              (항상 공인DNS)
```

**왜 2대인가:**  
시나리오 2에서 온프레미스가 응답 지연/Error 급증 → Locust-A 스레드 쌓임.  
1대면 이 지연이 EKS 부하에도 영향 → 실험 결과 오염.  
2대로 분리하면 한쪽이 터져도 다른 쪽 부하는 독립 유지.

**동시 시작: Locust 스케줄 기능**
```bash
# 두 EC2에서 동일 시각에 실행 (예: 14:00:00 정각)
# Locust-A
locust -f locustfile.py --host http://<온프레미스-IP> \
  --headless --users 200 --spawn-rate 50 --run-time 20m

# Locust-B
locust -f locustfile.py --host http://<ALB-DNS> \
  --headless --users 200 --spawn-rate 50 --run-time 20m
```
동일 스크립트를 GitHub 공통 레포에서 pull 후 실행.

**2계정 전환 시 변경:**  
Locust-B EIP → EKS 계정 VPC-B로 이동 or EKS 계정에 새 Locust-B 생성.  
Locust-A 타겟 IP만 사설→공인으로 변경.

### 1-4. ECR — 공유 or 각 계정에 따로?

**상황:**  
Docker 이미지는 완전히 동일해야 한다. 어느 레지스트리에서 pull할 것인가?

**옵션 A: 온프레미스 팀 계정 ECR → EKS 팀이 cross-account pull**

```
GitHub Actions → 온프레미스 계정 ECR에 push
EKS 계정: ECR 리소스 정책으로 cross-account pull 허용
```

- 단점: cross-account ECR 정책 설정 복잡

**옵션 B: 각 계정에 ECR, CI/CD가 양쪽에 동시 push**

```
GitHub Actions
  ├── 온프레미스 계정 ECR에 push (tag: v1.0.0)
  └── EKS 계정 ECR에 push (tag: v1.0.0, 동일 이미지)
```

- 장점: 독립적, 각 계정에서 직접 pull
- 단점: GitHub Actions에 두 계정의 IAM credentials 등록 필요

**→ ✅ 결정: 계정 구조에 따라 결정**
- 단일 계정: ECR 1개 공유 (같은 계정이므로 cross-account 불필요)
- 2계정 전환 시: 각 계정 ECR에 동일 이미지 push (GitHub Actions credentials 2개 등록)

### 1-6. k8s 버전

온프레미스와 EKS가 완전히 동일한 버전이어야 한다.  
EKS에서 지원하는 버전 중 최신 안정 버전으로 맞춘다.

```bash
# EKS 지원 버전 확인
aws eks describe-addon-versions --query 'addons[0].addonVersions[0].compatibilities[*].clusterVersion'
```

**→ 결정 필요: EKS 지원 최신 안정 버전으로 양쪽 동일하게**

### 1-7. 실험 동시 시작 방법

두 환경이 동시에 시나리오를 시작해야 공정한 비교가 된다.

**옵션 A: 구두 카운트다운 (Slack/화상통화 "3, 2, 1, 시작")**  
**옵션 B: Locust 스케줄 기능 (특정 시각에 자동 시작)**  
**옵션 C: GitHub Actions workflow dispatch (동시 트리거)**

**→ ✅ 결정: 옵션 B — Locust 스케줄 기능**  
`--run-time` + `--headless` + `--spawn-rate` 조합으로 특정 시각에 자동 시작.  
두 환경 동시 시작 시각을 스크립트에 고정해서 사람 개입 없이 동기화.
