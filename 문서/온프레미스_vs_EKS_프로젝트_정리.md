# 온프레미스 k8s vs AWS EKS 비교 실험 프로젝트

---

## 방향성

> "온프레미스 vs EKS, 어느 쪽이 우리 비즈니스에 맞는가"를 데이터로 보여준다.

대놓고 "EKS가 더 좋다"로 가지 않는다.
**"운영 특성 비교"** 프레임으로 가져간다.

발표를 듣는 사람이 스스로 결론을 내리게 만드는 것이 목표다.

---

UI 완성도:     30점으로 충분
API 로직:      100점
DB 정합성:     100점
실험 재현성:   100점

## 스토리 흐름

```
1단계 — 문제 제기
"타임세일 이벤트, 우리는 얼마나 잃고 있나?"

2단계 — 실험 소개
"동일한 앱, 동일한 트래픽, 다른 인프라"
"공정한 조건에서 비교했습니다"

3단계 — 시나리오 1 (일반 트래픽)
"이 상황에서는 온프레미스도 충분합니다"
→ 신뢰감 형성

4단계 — 시나리오 2 (트래픽 폭증)
"여기서 갈립니다"
→ 데이터가 말하게 한다

5단계 — 시나리오 3 (장애 상황)
"운영 관점에서 이런 차이가 납니다"
→ 비용이 아닌 운영 리소스 차이로 어필

6단계 — 결론
"이 차이가 비즈니스에 미치는 임팩트는 이렇습니다"
```

```
반드시 같아야 하는 것:
- Docker 이미지 (완전히 동일한 버전)
- Locust 스크립트 (GitHub 공통 레포 관리)
- RPS 설정 (동일한 부하량)
- 실험 시간 (동일한 시간대, 동시 시작)

달라도 되는 것:
- EC2 스펙 (의도적으로 다름)
- 노드 확장 방식 (실험 핵심 변수)
- 모니터링 서버 위치
```

## 전체 구조

```
팀 A 계정 — 온프레미스 재현
└── EC2 1대 (c8i.2xlarge)
    └── KVM VM
        ├── VM1: k8s 마스터
        ├── VM2: 워커노드 1  (t3.medium급 2vCPU / 4GB)
        └── VM3: 워커노드 2  (t3.medium급 2vCPU / 4GB)
└── EC2 1대 (t3.large)
    ├── Prometheus + Grafana (모니터링)
    └── CI/CD (GitHub Actions Runner)

팀 B 계정 — AWS EKS
└── EKS 클러스터
    ├── 워커노드 t3.medium × 2 (시작)
    └── Karpenter → t3.medium 자동 추가

공통 — 부하 테스트
└── EC2 1대 (t3.large)
    └── Locust
```

## EC2 스펙

| 용도 | 인스턴스 | vCPU | RAM | 시간당 비용 |
|---|---|---|---|---|
| 온프레미스 재현 | c8i.2xlarge | 8 | 16GB | $0.34/h |
| 모니터링 + CI/CD | t3.large | 2 | 8GB | $0.08/h |
| 부하 테스트 (Locust) | t3.large | 2 | 8GB | $0.08/h |
| EKS 워커노드 (시작) | t3.medium × 2 | 2 | 4GB | $0.04/h × 2 |

### 온프레미스 VM 구성 (c8i.2xlarge 내부)

| VM | 역할 | vCPU | RAM |
|---|---|---|---|
| VM1 | k8s 마스터 | 2 | 4GB |
| VM2 | 워커노드 1 | 2 | 4GB |
| VM3 | 워커노드 2 | 2 | 4GB |
| 합계 | | 6 + 오버헤드 | 12GB + 오버헤드 |

> 워커노드 VM 스펙 = EKS 워커노드 스펙 (t3.medium급)
> 공정한 비교를 위해 동일하게 맞춤

## 모니터링

### 수집 방법

| 수집 도구 | 대상 | 수집 지표 |
|---|---|---|
| prom-client | Next.js 앱 | TPS, Latency, Error Rate, API별 응답시간 |
| kube-state-metrics | k8s 클러스터 | Pod 수, Node 수, Pending Pod, HPA 상태 |
| Node Exporter | VM / 노드 | CPU, RAM, 디스크, 네트워크 |

### 시각화

```
Prometheus → 지표 수집 및 저장
Grafana    → 대시보드 시각화
CloudWatch → EKS 보조 모니터링 (선택)

모니터링 서버 위치:
팀 A EC2 (t3.large) 안에 구성
Prometheus가 온프레미스 k8s + EKS 양쪽 동시 scrape
→ Grafana 하나에서 양쪽 나란히 비교
```

### 직접 제작 패널 (8개)

#### 상단 — 비즈니스 지표 (온프레미스 | EKS 나란히)

```
1. TPS (초당 트랜잭션 수)
   - 수집: prom-client
   - 보여줄 것: 트래픽 폭증 시 처리량 차이
   - 형태: 라인 그래프 (양쪽 비교)

2. P95 Latency (95번째 백분위 응답시간)
   - 수집: prom-client
   - 보여줄 것: 폭증 시 응답시간이 얼마나 튀는지
   - 형태: 라인 그래프 (양쪽 비교)

3. Error Rate (에러 비율)
   - 수집: prom-client
   - 보여줄 것: 504/500 에러 발생률
   - 형태: 라인 그래프 (양쪽 비교)
   - 핵심: 온프레미스 치솟고 EKS 0% 유지
```

#### 중단 — k8s 반응

```
4. Pod Count 타임라인
   - 수집: kube-state-metrics
   - 보여줄 것: 시간 흐름에 따른 Pod 개수 변화
   - 형태: 라인 그래프 (양쪽 비교)
   - 핵심: "트래픽 증가 → 자동 확장" 흐름

5. Node Count 타임라인
   - 수집: kube-state-metrics
   - 보여줄 것: EKS 노드가 자동으로 늘어나는 순간
   - 형태: 라인 그래프 (양쪽 비교)
   - 핵심: 온프레미스 고정 / EKS 자동 증가

6. Pending Pod 타임라인
   - 수집: kube-state-metrics
   - 보여줄 것: 자원 부족으로 대기 중인 Pod 수
   - 형태: 라인 그래프 (양쪽 비교)
   - 핵심: 온프레미스 계속 쌓임 / EKS 0 유지
   - 발표 임팩트: 가장 강력한 한 방

7. HPA current vs desired replicas
   - 수집: kube-state-metrics
   - 보여줄 것: HPA가 원하는 Pod 수 vs 실제 Pod 수
   - 형태: 라인 그래프 2개
   - 핵심: 괴리가 크면 노드 부족 상태
```

#### 하단 — API 상세

```
8. API 엔드포인트별 응답시간
   - 수집: prom-client
   - 보여줄 것: /products / /orders / /payments 각각 응답시간
   - 형태: 라인 그래프 3개
   - 핵심: 어느 서비스에서 병목 발생하는지
```

## 시나리오

### 시나리오 1 — 일반 트래픽 (20분)

```
상황:
평상시 쇼핑몰 운영 상태

부하:
100~200 RPS 유지

진행:
워밍업 5분 → 정상 트래픽 10분 → 관찰 5분

핵심 서비스:
전체 서비스 고르게

보여줄 것:
- TPS 안정적
- Error Rate 0%
- Pod 수 변화 없음
- 둘 다 정상 운영

메시지:
"트래픽이 예측 가능하고 안정적이면
 온프레미스도 충분합니다"
```

### 시나리오 2 — 타임세일 트래픽 폭증 (20분)

```
상황:
타임세일 시작 순간 트래픽 급증

부하:
100 RPS → 1000 RPS 급증

진행:
정상 트래픽 5분 → 폭증 10분 → 안정화 관찰 5분

핵심 서비스:
Product Service (Read 폭증)
Inventory Service (동시성 집중)

온프레미스 예상:
- Pending Pod 쌓임
- Error Rate 급증
- 재고 차감 실패 발생

EKS 예상:
- Node 자동 추가 (90초)
- Pod 자동 확장
- Error Rate 0% 유지

보여줄 것:
- Pending Pod 타임라인 (가장 강력)
- Node Count 자동 증가 (EKS)
- Error Rate 차이
- 재고 차감 실패 건수

메시지:
"예측 불가능한 폭증이 발생하는 순간
 운영 방식의 차이가 비즈니스 임팩트로 이어집니다"
```

### 시나리오 3 — 노드 장애 복구 (20분)

```
상황:
피크 트래픽 중 워커노드 1대 강제 종료

부하:
500 RPS 유지 중 장애 발생

진행:
피크 트래픽 5분 → 노드 강제 종료 → 복구 관찰 10분 → 정상 확인 5분

핵심 서비스:
Order Service (Write 트래픽)
Payment Service (정합성 핵심)

온프레미스 예상:
- Pod 재스케줄 5~10분 소요
- 그 동안 결제 실패 N건 발생
- 수동 개입 필요

EKS 예상:
- 자동 복구 30~60초
- 결제 실패 최소화
- 운영자 개입 없음

보여줄 것:
- MTTR (평균 복구 시간) 비교
- 장애 중 결제 실패 건수
- 주문 데이터 정합성 유지 여부

메시지:
"복구 시간의 차이가
 운영 리소스와 고객 경험의 차이로 이어집니다"
```
