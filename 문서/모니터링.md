## 1. 수집 구조

```
온프레미스 k8s 클러스터          AWS EKS 클러스터
  ├─ prom-client (앱)              ├─ prom-client (앱)
  ├─ kube-state-metrics            ├─ kube-state-metrics
  ├─ Node Exporter                 ├─ Node Exporter
  ├─ PostgreSQL Exporter           ├─ PostgreSQL Exporter (RDS)
  └─ Redis Exporter                └─ Redis Exporter
          │                                 │
          └───────────┬─────────────────────┘
                      ↓ scrape (5초 간격)
              Prometheus (t3.small EC2)
                      ↓
              Grafana (t3.small EC2)
                      ↓
        ┌─────────────────────────────┐
        │  온프레미스  │  AWS EKS     │  ← 나란히 비교
        └─────────────────────────────┘
```

> Prometheus 하나가 양쪽 클러스터를 동시 scrape한다.
> Grafana에서 `datasource` 변수로 온프레미스 / EKS를 전환해 동일 패널에 나란히 표시.

## 2. 수집 도구별 역할

| 수집 도구 | 설치 위치 | 수집 대상 | 주요 메트릭 |
|---|---|---|---|
| **prom-client** | Express.js 앱 내부 | API 요청/응답 | TPS, Latency, Error Rate, API별 응답시간 |
| **kube-state-metrics** | k8s 클러스터 내부 | k8s 오브젝트 상태 | Pod 수, Node 수, Pending Pod, HPA 상태 |
| **Node Exporter** | 각 워커노드 | 노드 인프라 | CPU, Memory, 디스크, 네트워크 I/O |
| **PostgreSQL Exporter** | k8s 외부 EC2 | PostgreSQL DB | Active Connection, 쿼리 속도, Lock 대기 |
| **Redis Exporter** | k8s 외부 EC2 | Redis 캐시 | 캐시 히트율, 메모리 사용량, 명령 처리량 |

## 3. Grafana 템플릿 패널

Grafana 공식 대시보드 템플릿을 **Import**하고, 필요한 패널만 골라 최종 대시보드에 붙여 넣는다.

---

### 3-1. Node Exporter Full — ID: `1860`

**Import 주소:** `grafana.com/dashboards/1860`

**가져올 패널:**

| 패널명 | 원본 패널 위치 | 용도 |
|---|---|---|
| CPU 사용률 | CPU Basic → CPU Usage | 노드 전체 CPU 점유율 추이 |
| Memory 사용률 | Memory Basic → Memory Usage | 가용 메모리 감소 추이 |
| Network I/O | Network Traffic → Network Bandwidth | 트래픽 폭증 시 네트워크 포화 여부 |

**가져올 때 설정:**

```
Datasource : Prometheus (온프레미스 or EKS)
Job        : node-exporter
Instance   : 워커노드 IP 선택
```

---

### 3-2. Kubernetes Cluster Monitoring — ID: `315`

**Import 주소:** `grafana.com/dashboards/315`

**가져올 패널:**

| 패널명 | 원본 패널 위치 | 용도 |
|---|---|---|
| Pod Count | Pods → Running Pods | Running 상태 Pod 수 타임라인 |
| Node Count | Nodes → Cluster Nodes | 노드 수 — EKS Karpenter 자동 추가 순간 포착 |
| Pending Pod | Pods → Pending Pods | **발표 핵심** — 온프레미스 쌓임 / EKS 0 유지 |

**가져올 때 설정:**

```
Datasource  : Prometheus
Namespace   : default (또는 서비스 namespace)
```

---

### 3-3. PostgreSQL Database — ID: `9628`

**Import 주소:** `grafana.com/dashboards/9628`

**가져올 패널:**

| 패널명 | 원본 패널 위치 | 용도 |
|---|---|---|
| Active Connection | Connections → Active Connections | 동시 접속자 수 — 폭증 시 병목 확인 |
| 쿼리 응답시간 | Query Performance | 느려지는 쿼리 구간 특정 |
| Lock 대기 | Locks → Locks by Database | `SELECT FOR UPDATE` / 낙관적 락 충돌 시각화 |

**가져올 때 설정:**

```
Datasource  : Prometheus
Job         : postgres-exporter
Datname     : shoply
```

---

### 3-4. Redis Dashboard — ID: `11835`

**Import 주소:** `grafana.com/dashboards/11835`

**가져올 패널:**

| 패널명 | 원본 패널 위치 | 용도 |
|---|---|---|
| 캐시 히트율 | Stats → Hit Rate | 히트율 낮으면 DB 직접 조회 폭증 신호 |
| Memory 사용량 | Memory → Used Memory | Redis 메모리 포화 여부 |
| 명령 처리량 | Stats → Commands per sec | 초당 Redis 명령 수 — 캐시 효과 확인 |

**가져올 때 설정:**

```
Datasource  : Prometheus
Job         : redis-exporter
Addr        : redis:6379
```

## 4. 직접 제작 패널

템플릿에 없거나 **양쪽 환경을 나란히 비교**해야 하는 패널은 직접 만든다.  
모두 Grafana → `Add panel → Time series` 로 생성.

---

### 4-1. TPS (초당 트랜잭션 수)

| 항목 | 내용 |
|---|---|
| 수집 도구 | prom-client |
| 패널 타입 | Time series |
| 목적 | 트래픽 폭증 시 양쪽 처리량 차이 |

**PromQL:**

```promql
# 온프레미스
rate(http_requests_total{job="msa-app", env="onprem"}[1m])

# EKS
rate(http_requests_total{job="msa-app", env="eks"}[1m])
```

**앱에서 노출해야 할 메트릭:**

```javascript
// prom-client 예시 (Express.js)
const httpRequestsTotal = new Counter({
  name: 'http_requests_total',
  help: 'Total HTTP requests',
  labelNames: ['method', 'path', 'status'],
});
```

**발표 포인트:** 시나리오 2에서 온프레미스 TPS가 한계에 걸려 수평으로 꺾이는 구간

---

### 4-2. P95 Latency (95번째 백분위 응답시간)

| 항목 | 내용 |
|---|---|
| 수집 도구 | prom-client |
| 패널 타입 | Time series |
| 단위 | seconds (s) |
| 목적 | 폭증 구간에서 응답시간이 얼마나 튀는지 |

**PromQL:**

```promql
# 온프레미스
histogram_quantile(0.95,
  rate(http_request_duration_seconds_bucket{job="msa-app", env="onprem"}[1m])
)

# EKS
histogram_quantile(0.95,
  rate(http_request_duration_seconds_bucket{job="msa-app", env="eks"}[1m])
)
```

**앱에서 노출해야 할 메트릭:**

```javascript
const httpRequestDuration = new Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP request duration in seconds',
  labelNames: ['method', 'path', 'status'],
  buckets: [0.01, 0.05, 0.1, 0.3, 0.5, 1, 2, 5],
});
```

---

### 4-3. Error Rate (에러 비율)

| 항목 | 내용 |
|---|---|
| 수집 도구 | prom-client |
| 패널 타입 | Time series |
| 단위 | percent (0~1) |
| 목적 | 5xx 에러 비율 — **발표 임팩트 최강** |

**PromQL:**

```promql
# 온프레미스
rate(http_requests_total{job="msa-app", env="onprem", status=~"5.."}[1m])
/
rate(http_requests_total{job="msa-app", env="onprem"}[1m])

# EKS
rate(http_requests_total{job="msa-app", env="eks", status=~"5.."}[1m])
/
rate(http_requests_total{job="msa-app", env="eks"}[1m])
```

**발표 포인트:** 시나리오 2에서 온프레미스 37% vs EKS 0.3% 대비

---

### 4-4. Pod Count 타임라인

| 항목 | 내용 |
|---|---|
| 수집 도구 | kube-state-metrics |
| 패널 타입 | Time series |
| 목적 | HPA 발동으로 Pod가 늘어나는 흐름 |

**PromQL:**

```promql
# Running Pod 수 (온프레미스)
count(kube_pod_status_phase{phase="Running", cluster="onprem"})

# Running Pod 수 (EKS)
count(kube_pod_status_phase{phase="Running", cluster="eks"})
```

---

### 4-5. Node Count 타임라인

| 항목 | 내용 |
|---|---|
| 수집 도구 | kube-state-metrics |
| 패널 타입 | Time series |
| 목적 | EKS Karpenter로 노드가 자동 추가되는 순간 |

**PromQL:**

```promql
# 온프레미스 (고정 2개 — 변하지 않음)
count(kube_node_info{cluster="onprem"})

# EKS (Karpenter로 자동 증가)
count(kube_node_info{cluster="eks"})
```

**발표 포인트:** 온프레미스는 수평선, EKS는 트래픽 폭증 90초 후 계단식 상승

---

### 4-6. Pending Pod 타임라인

| 항목 | 내용 |
|---|---|
| 수집 도구 | kube-state-metrics |
| 패널 타입 | Time series |
| 목적 | 자원 부족으로 스케줄 못 받은 Pod 수 |

**PromQL:**

```promql
# 온프레미스 (쌓임)
count(kube_pod_status_phase{phase="Pending", cluster="onprem"})

# EKS (0 유지)
count(kube_pod_status_phase{phase="Pending", cluster="eks"})
```

**발표 포인트:** 이 패널 하나가 모든 것을 설명한다  
온프레미스 — 계속 쌓임 / EKS — 0 유지

---

### 4-7. HPA current vs desired

| 항목 | 내용 |
|---|---|
| 수집 도구 | kube-state-metrics |
| 패널 타입 | Time series (2개 선) |
| 목적 | HPA가 원하는 Pod 수와 실제 Pod 수의 괴리 |

**PromQL:**

```promql
# desired replicas
kube_horizontalpodautoscaler_spec_max_replicas{cluster="onprem"}

# current replicas
kube_horizontalpodautoscaler_status_current_replicas{cluster="onprem"}
```

**읽는 법:** desired > current 구간 = 노드 자원 부족으로 Pod를 못 띄우는 상태

### 4-11. Redis 캐시 히트율

| 항목 | 내용 |
|---|---|
| 수집 도구 | Redis Exporter |
| 패널 타입 | Time series |
| 단위 | percent (0~1) |
| 목적 | 히트율 낮으면 DB 직접 조회 폭증 신호 |

**PromQL:**

```promql
rate(redis_keyspace_hits_total{cluster="onprem"}[1m])
/
(
  rate(redis_keyspace_hits_total{cluster="onprem"}[1m])
  +
  rate(redis_keyspace_misses_total{cluster="onprem"}[1m])
)
```

### 4-12. API 엔드포인트별 응답시간

| 항목 | 내용 |
|---|---|
| 수집 도구 | prom-client |
| 패널 타입 | Time series (엔드포인트별 각 선) |
| 목적 | 어느 서비스에서 병목이 발생하는지 특정 |

**PromQL:**

```promql
histogram_quantile(0.95,
  sum by (path, le) (
    rate(http_request_duration_seconds_bucket{
      job="msa-app",
      env="onprem",
      path=~"/api/(products|orders|payments).*"
    }[1m])
  )
)
```

**확인 포인트:** 시나리오 2에서 `/api/products`가 먼저 튀는지, `/api/orders`가 먼저 튀는지

## 6. 시나리오별 주목 패널

### 시나리오 2 — 타임세일 폭증

| #5 Node Count | 2개 고정 | 2 → 4~5개 | Karpenter 발동 |

### 시나리오 3 — 노드 장애

| 주목 패널 | 온프레미스 | EKS | 의미 |
