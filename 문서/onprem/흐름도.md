# D. 흐름도

> 두 가지 관점의 흐름을 다룬다.
> **사용자 흐름** = 쇼핑몰 이용자가 요청을 보낼 때 트래픽이 흐르는 경로.
> **엔지니어 흐름** = 구축·배포·실험을 수행하는 작업 순서.

---

## 1. 사용자 흐름 (트래픽 경로)

### 1.1 요청 진입 경로 (온프레미스)

```mermaid
flowchart TB
  U["사용자 / k6<br/>shoply.example.com"]
  EIP["c8i EC2 (EIP 공인IP)<br/>:80 / :443"]
  DNAT["호스트 iptables DNAT<br/>(-d 호스트IP)"]
  VIP["MetalLB VIP 192.168.122.24x<br/>(worker3 L2/ARP 광고)"]
  ING["Nginx Ingress Pod (worker3)"]
  GW["API Gateway :4000"]
  SVC["각 마이크로서비스 Pod"]
  DB[("PostgreSQL / Redis")]

  U -->|"http(s)"| EIP
  EIP --> DNAT
  DNAT --> VIP
  VIP --> ING
  ING -->|"/api/*"| GW
  ING -->|"/"| FE["Frontend :80"]
  GW --> SVC
  SVC --> DB
```

> KVM VM에 공인 IP가 없어 EC2가 80/443을 받아 MetalLB VIP로 넘기는 **NAT 포워딩 홉**이 한 번 더 있다(EKS엔 없음 → 변화율%로 보정).

### 1.2 사용자 시나리오 흐름 (쇼핑 플로우)

```mermaid
flowchart LR
  A["홈 접속"] --> B["로그인<br/>(test1~2000)"]
  B --> C["상품 조회<br/>(Product, 캐시)"]
  C --> D["주문 생성<br/>(Order → 재고 예약)"]
  D --> E["결제<br/>(Payment, Mock 95%)"]
  E -->|성공| F["재고 차감 + 주문완료"]
  E -->|실패| G["예약 해제"]
```

### 1.3 요청 라우팅 규칙

| 경로 | 도착 |
|---|---|
| `/` | Frontend |
| `/api/products` | Product |
| `/api/inventory` | Inventory |
| `/api/orders` | Order |
| `/api/payments` | Payment |
| `/api/auth` | User |

## 2. 엔지니어 흐름 (구축 → 배포 → 실험)

### 2.1 전체 작업 흐름

```mermaid
flowchart TB
  subgraph BUILD["① 앱 빌드"]
    s1["7개 서비스 개발"] --> s2["Dockerfile"] --> s3["git push → GitHub Actions → GHCR"]
  end
  subgraph INFRA["② 온프레미스 인프라"]
    i1["EC2(중첩가상화) 기동"] --> i2["KVM VM 4대 생성<br/>(cloud-init)"]
    i2 --> i3["kubeadm init + join"] --> i4["Flannel·Ingress·MetalLB"]
    i4 --> i5["worker3 taint 격리<br/>+ iptables DNAT"]
  end
  subgraph DEPLOY["③ 서비스 배포"]
    d1["매니페스트<br/>(Deploy/HPA/ConfigMap/Secret/Ingress)"] --> d2["kubectl apply"]
    d2 --> d3["배포 검증<br/>(로그인·주문·결제)"]
  end
  subgraph EXP["④ 실험"]
    e1["load-test-prep.sql<br/>재고 리셋"] --> e2["capture-loop.sh 캡처 시작"]
    e2 --> e3["k6 부하 (계단식 ↑)"]
    e3 --> e4["Pending 발생 = 한계"]
    e4 --> e5["analyze_experiment.py<br/>→ HTML 리포트"]
  end
  BUILD --> INFRA --> DEPLOY --> EXP
```

### 2.2 인프라 구축 상세 흐름

```mermaid
flowchart TB
  a["중첩가상화 Launch Template"] --> b["c8i.2xlarge 스팟 기동"]
  b --> c["KVM/libvirt 설치"]
  c --> d["cloud-init으로 VM 4대 초기화<br/>master/worker1·2·3"]
  d --> e["각 VM: containerd·kubeadm·kubelet"]
  e --> f["master: kubeadm init<br/>(ip_forward 선적용)"]

```

### 2.3 실험 측정 흐름 (한계 RPS 찾기)

```mermaid
flowchart TB
  p1["load-test-prep.sql 실행"] --> p2["Grafana 대시보드 띄움"]
  p2 --> p3["capture-loop.sh 켜기"]
  p3 --> p4["k6: 낮은 VU부터 시작"]
  p4 --> p5{"계단식으로 VU ↑<br/>매 단계 확인"}
  p5 -->|"Pending 없음"| p4
  p5 -->|"Pending 발생"| p6["그 순간 증거 5종 캡처"]
  p6 --> p7["describe로 원인 검증<br/>(Insufficient cpu?)"]
  p7 --> p8["run 폴더 → analyze_experiment.py<br/>→ HTML 리포트"]
```

| 한계 신호 | 확인 |
|---|---|
| **Pending 발생** ★ | `kubectl get pods --field-selector=status.phase=Pending` |
| 워커 CPU 90%+ | `kubectl top nodes` |
| HPA CURRENT=MAX | `kubectl get hpa` |

> **한계의 정의 = Pending Pod이 처음 뜨는 지점.** 원인이 `Insufficient cpu`여야 "고정 자원 한계"로 유효.

### 2.4 시나리오 진행 흐름

```mermaid
flowchart LR

```

## 3. 장애·복구 흐름 (시나리오 3)

```mermaid
flowchart TB
  n["worker1 강제 종료<br/>(Ingress·Gateway·Product·Inventory 다운)"]
  n --> resch["모든 파드 worker2로 재스케줄"]
  resch --> pend["worker2(2c/4G) 자원 부족 → Pending"]
  pend --> onprem["온프레: 사람이 노드 수동 재시작<br/>(virsh start) — 분 단위"]
  pend --> eks["EKS(예정): Karpenter 새 노드 자동 추가<br/>— ~60초"]
```

> 복구 시간(MTTR) = 비즈니스 손실. 장애 중 결제 실패 건수를 매출 손실로 환산한다.
