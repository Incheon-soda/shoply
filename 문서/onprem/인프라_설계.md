# 인프라 설계 — 온프레미스 k8s (AWS EC2 + KVM)

> 온프레미스 Kubernetes를 AWS EC2 위 KVM 가상머신으로 재현한 인프라의 **설계와 구축**.
> 설계 의도·핵심 결정 중심으로 정리하고 단계별 명령은 요점만 둔다. (상세 장애 대응 → `트러블슈팅.md`)

---

## 1. 설계 목표

| 목표 | 내용 |
|---|---|
| **재현 가능성** | 설치 절차를 고정해 누가 해도 같은 클러스터가 나오게 (AI 가이드 따라가다 항목 누락→재설치 반복을 겪고 절차를 문서로 못박음) |
| **실험/운영 분리** | 운영 보조 파드가 실험 워커 자원을 갉아먹지 않게 노드를 분리 → "고정 자원의 순수 한계" 측정 |
| **EKS와 동일화** | 노드 자동확장만 빼고 전부 같게 → 진입 LB·버전·리소스를 EKS와 대칭으로 |

---

## 2. 환경 구성

| 항목 | 값 |
|---|---|
| 호스트 EC2 | c8i.2xlarge (8 vCPU/16 GB, 스팟, 공인IP), Ubuntu 24.04 |
| 가상화 | KVM (중첩 가상화 활성) |
| VM | master + worker1·2(실험) + worker3(운영) = **4대**, 각 2 vCPU/4 GB |
| VM OS | Ubuntu 24.04 cloud image + cloud-init |
| K8s | v1.34.8 (EKS와 동일) |
| CNI | Flannel v0.26.7 |
| 진입 | EIP → 호스트 iptables DNAT → MetalLB VIP(worker3) → Nginx Ingress |

### 노드 역할

| VM | 역할 | 라벨 / taint |
|---|---|---|
| master | 컨트롤플레인 (kubeadm) | — |
| worker1 | 실험: gateway·product·inventory | `experiment-role=worker1` |
| worker2 | 실험: frontend·order·payment·user | `experiment-role=worker2` |
| worker3 | 운영: Ingress·MetalLB·metrics | `experiment-role=ops` + `dedicated=ops:NoSchedule` |

---

## 3. 노드 설계 — 실험/운영 분리 (핵심 결정)

워커 2대만 쓰면 Nginx Ingress·kube-state-metrics 같은 **운영 보조 파드**가 실험 워커 위에서 같이 돌며 CPU/메모리를 갉아먹어 "고정 자원의 순수 한계" 측정을 흐린다. worker3에 **taint**를 걸어 앱 파드가 절대 못 들어가게 막고, 운영 컴포넌트만 toleration으로 들여보낸다.

| | 워커 2대 | **워커 3대 (채택)** |
|---|---|---|
| 실험 파드 | 운영 파드와 섞임 | worker1·2 전용 |
| HPA 폭증 시 | 운영 파드와 자원 경합 | 실험 워커만 터짐(운영 안전) |
| 측정 신뢰도 | 오버헤드 섞임 | **순수 앱 부하만** |

```bash
# 9단계 - 노드 역할 부여 (master VM)
kubectl label node k8s-worker1 experiment-role=worker1
kubectl label node k8s-worker2 experiment-role=worker2
kubectl label node k8s-worker3 experiment-role=ops
# ★ worker3 taint — toleration 없는 파드는 절대 못 들어옴
kubectl taint node k8s-worker3 dedicated=ops:NoSchedule
```

## 4. 구축 흐름 (요약)

| 단계 | 핵심 | 주의/결정 |
|---|---|---|
| 0 중첩 가상화 | Launch Template로 활성화 | 스팟 요청엔 옵션 없어 템플릿 필요. `grep -c 'vmx\|svm' /proc/cpuinfo` 확인 |
| 1 디스크 확장 | root EBS 150GB (`growpart`+`resize2fs`) | VM 4대분 여유 |
| 2 KVM 설치 | qemu-kvm·libvirt·virtinst·cloud-image-utils | — |
| 3 VM 4대 | cloud image backing qcow2 + cloud-init, `virt-install` | **MAC 고정 → DHCP 예약으로 IP 고정**(재부팅·복원해도 인증서·configmap 안 깨짐) |
| 3-1 DNS | `/etc/resolv.conf` 8.8.8.8 직접 | KVM에서 systemd-resolved 불통 → 안 하면 ghcr pull·helm 실패 |
| 4 공통 OS | swap off, `overlay`/`br_netfilter`, sysctl `ip_forward=1` | **ip_forward 누락 시 kubeadm init 전 수동 적용** |
| 5 containerd | `SystemdCgroup=true` | — |
| 6 kubeadm/kubelet/kubectl | **1.34.8** 고정(`apt-mark hold`) | repo 줄은 한 줄(줄바꿈 시 malformed) |
| 7 init + join | master `kubeadm init --pod-network-cidr=10.244.0.0/16`, worker3대 join | — |
| 8 Flannel | `kube-flannel.yml v0.26.7` | crash 시 br_netfilter 재확인 |
| 9 라벨 + taint | 3절 참고 | — |
| 10 Ingress→worker3 | helm ingress-nginx, toleration+nodeSelector로 worker3 배치 | — |
| 11 metrics-server | `--kubelet-insecure-tls` | KVM 필수. HPA가 CPU 못 읽으면 이것부터 |
| 12 배포 | worker1·2에만 앱 배포 (soft affinity) | 4절 진입·6절 모니터링 병행 |

## 5. 진입 경로 설계 — MetalLB + iptables DNAT

KVM VM에 공인 IP가 없어, 호스트 EC2가 80/443을 받아 클러스터로 넘기는 NAT 포워딩을 한다.

```
사용자/k6 → EIP(c8i EC2) :80/443
  → 호스트 iptables DNAT (-d 호스트IP)        ← VM에 공인IP 없음
  → MetalLB VIP 192.168.122.24x (worker3 L2/ARP 광고)
  → Nginx Ingress Pod (worker3) → /api→Gateway, /→Frontend
```

- **MetalLB**: ingress-nginx를 `type: LoadBalancer`로 노출 → 사설 VIP를 worker3가 광고. speaker에 toleration을 줘 worker3(taint)에도 뜨게 한다. **EKS NLB와 같은 추상화**라 진입 경로가 대칭이 되어 공정 비교가 성립한다.
- **호스트 DNAT 주의**: `-d 호스트IP`를 반드시 붙인다. 안 붙이면 워커의 `ghcr.io` pull(443)까지 가로채 ImagePullBackOff. 호스트 사설IP는 재구축마다 바뀌므로 `host-network.sh`가 자동 감지.
- **EKS 대칭(예정)**: EKS는 ingress-nginx를 `LoadBalancer`로 두면 NLB가 자동 생성 → 온프레 MetalLB VIP와 대칭. Ingress부터 백엔드까지 완전 동일.

## 6. 서비스 배포 설계

서비스별 매니페스트: Deployment / Service(ClusterIP·NodePort) / HPA / ConfigMap / Secret / Ingress.

- **배치**: soft nodeAffinity로 worker1·2에만 초기 배치, HPA 추가분은 자유. HPA `min 1 / max 99`(한계 관찰용), target 60%, request 100m/limit 500m.
- **ConfigMap**: `POSTGRES_HOST`/`REDIS_HOST`에 DB·Redis EC2 **사설 IP**(EC2 재생성마다 바뀜 → 옛 IP면 백엔드 0/1).
- **gateway alias Service(필수)**: frontend의 nginx.conf가 upstream을 `gateway:4000`으로 하드코딩했는데 실제 Service명은 `gateway-svc`라 DNS 실패 → 재빌드 없이 같은 selector(`app: gateway`)의 `gateway` Service를 하나 더 만들어 해결.
- **격리 검증**: worker1·2엔 앱 파드만, worker3엔 운영 파드만. 부하로 HPA가 늘려도 worker3엔 앱 파드가 안 가야 정상.

## 7. 모니터링 메트릭 노출 (iptables 포워딩)

VM이 NAT 뒤라, 메트릭 NodePort를 호스트 iptables DNAT로 외부 Prometheus에 노출한다.

| 대상 | 포트 | 배치 |
|---|---|---|
| 앱 prom-client | 30400~30404 | master VM로 DNAT |
| kube-state-metrics | 30800 | worker3 |
| node_exporter | 9100 / 39101·39102·39103 | 호스트 + 각 워커 |
| cAdvisor (파드별 CPU/메모리) | 38080·38081 | worker1·2 DaemonSet |

> SG-K8s 인바운드에 위 포트를 모니터링 SG 소스로 열어야 한다. 안 열면 `no route to host`. prometheus.yml의 K8s EC2 사설IP도 재생성 때마다 갱신(안 하면 타겟이 조용히 `down`).

## 8. 핵심 설계 결정·근거

| 결정 | 이유 |
|---|---|
| **KVM 가상머신** | "오토스케일링 없는 고정 자원" 온프레미스를 재현. (c8i 기본은 중첩가상화 미노출 → Launch Template로 활성화) |
| **worker3 taint 격리** | 운영 파드가 실험 워커 자원을 오염 → 격리해 순수 한계 측정 |
| **VM IP 고정(DHCP 예약)** | 재부팅·복원 시 IP 바뀌면 인증서·kubeconfig·ConfigMap 깨짐 |
| **HPA max 99** | max 제한하면 노드가 안 터져 "고정 자원 한계"(Pending)를 못 봄 |
| **MetalLB 진입** | EKS NLB와 같은 `LoadBalancer` 추상화 → 공정 비교 |
| **iptables `-d 호스트IP`** | 안 붙이면 ghcr pull(443)까지 가로채 ImagePullBackOff |

## 9. 주요 트러블슈팅 (요약)

| 증상 | 원인 | 해결 |
|---|---|---|
| ghcr pull 타임아웃 | KVM VM DNS 불통 | resolv.conf 8.8.8.8 직접 |
| kubeadm init 실패 | ip_forward 누락 | init 전 `sysctl -w net.ipv4.ip_forward=1` |
| Prometheus 30800/30400 불통 | iptables FORWARD 차단 | `iptables -I FORWARD -d/-s 192.168.122.0/24 -j ACCEPT` |
| flannel CrashLoop | br_netfilter 미로드 | 워커에서 `modprobe br_netfilter` 후 재생성 |
| apiserver 6443 refused | loopback 방화벽 | 방화벽 규칙 복구(트러블슈팅.md) |
| frontend CrashLoop | gateway DNS 실패 | gateway alias Service 추가 |
| 백엔드 0/1 | ConfigMap DB/Redis 옛 IP | 현재 사설IP로 patch |

> 전체 장애 사례·복구 절차는 `트러블슈팅.md` 참고.

## 부록 (선택) — ArgoCD (GitOps CD)

> 실험 본질(노드 자동확장)과 무관한 **운영 편의 도구**. 안 써도 실험은 성립한다. worker3 taint 격리 덕에 실험 워커를 오염시키지 않고 얹을 수 있어 "선택"으로 둔다.

- **개념**: `kubectl apply`를 손으로 안 하고 **Git에 매니페스트 push → ArgoCD가 자동 동기화**(배포 이력·롤백·드리프트 감지).
- **배치**: helm 글로벌 `nodeSelector(experiment-role=ops)` + `toleration(dedicated=ops)`로 **worker3에만** 배치.

```bash
helm repo add argo https://argoproj.github.io/argo-helm && helm repo update
helm install argocd argo/argo-cd -n argocd --create-namespace \
  --set global.nodeSelector."experiment-role"=ops \
  --set 'global.tolerations[0].key=dedicated' \
  --set 'global.tolerations[0].operator=Equal' \
  --set 'global.tolerations[0].value=ops' \
  --set 'global.tolerations[0].effect=NoSchedule' \
  --set server.service.type=NodePort --set server.service.nodePortHttp=30808 \
  --set dex.enabled=false --set applicationSet.enabled=false --set notifications.enabled=false
```

- **접속**: NodePort 30808 + 호스트 DNAT, 초기 비번 `kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d`.
- **앱 연결**: `Application` 리소스로 Git repo(`msa_shoply/.../k8s`) 연결 → `syncPolicy.automated`(prune·selfHeal)로 자동 배포.
- ⚠️ worker3(2core/4GB)에 ingress·kube-state·event-exporter가 이미 있어 빠듯 → 위처럼 dex·applicationSet·notifications 비활성화로 경량화.
- **공정성**: worker3 격리라 실험 워커 무오염. 측정엔 영향 없고, "배포를 GitOps로 한다"는 운영 성숙도를 발표에 더할 수 있다.
